# 多账号下的本地数据作用域

> **状态：已实现。** 2026-10-08 提出，同日落地。
> 起因是应用改名为「波纹音乐」时顺手改数据目录，发现本机数据**没有任何账号维度**。
>
> 实现与本文有三处差异，都是铺到代码里才看清的：
> 1. **`ICurrentAccount` 多暴露了 `Scope` 与 `Changed`**（原设计只有 `Uid`）。
>    `Scope` 免去每个调用点各写一次 `-1` 的特判；`Changed` 是「内存里那份也要跟着换」的唯一通知源。
> 2. **队列没有走「每次问当前账号」这条路**，改成由 `PlaybackCoordinator` 显式传作用域。
>    原因见第五节末尾：队列的内存副本由协调器长期持有且有防抖落盘，切号时必须先写回**旧**作用域，
>    而那一刻"当前是谁"已经是新账号了。
> 3. **「记住播放列表」开关从 `queue.json` 挪进了 `playback.json`。** 队列按账号分之后它也会被带走，
>    于是"为隐私关掉、换个号又自己打开"。它本质是个人级偏好，归位即可。
>    `playback.json` 的格式随之从裸枚举变成对象，读取保留了老格式的回落。

## 问题

应用支持登出后用另一个账号登入（`AccountViewModel.SignOut` → `AccountViewModel` 切回登录页）。
但**本地数据是一份平的**：换账号之后，前一个账号的播放队列、最近播放、搜索历史原样继承。

唯一有作用域概念的是服务端数据（我喜欢、歌单、关注），那些天然按账号走，不受影响。

## 现状（已核实，2026-10-08）

`AppPaths` 的 20 个路径全部平铺在 `%LOCALAPPDATA%\Bowen\` 下，**零账号维度**。
`JsonPlayHistoryStore` 的类注释还明确写着：

> 它记录的是「听过什么歌」——不是凭据，也不含任何账号标识（`uid` 不进去）。

也就是说「不带账号」当年是**刻意的**，不是漏掉的。所以这份文档要回答的不是「补上 uid」，
而是**「哪些东西本来就该按账号分」**。

## 一、三个作用域，别一刀切

把 20 项全按账号分是错的。按「换账号时该不该跟着换」分三类：

### 设备级 —— 跨账号共用是**要求**

| 项 | 为什么 |
| --- | --- |
| `devid.txt` | **设备标识。按账号分会变成 N 个设备标识**，而「频繁变更设备标识是账号风控的异常信号」是 `AppPaths` 自己写的。共用是要求，不是缺陷 |
| `logs/` | 诊断用。按账号分会让排查时要在几个目录里来回找 |
| `cache/covers/` | 公开封面的缓存，同名同内容。分开只是让磁盘多存几份 |

### 个人级 —— 跨账号共用**合理**

| 项 | 为什么 |
| --- | --- |
| `window.json`、`mini-player-window.json`、`desktop-lyrics-window.json` | 窗口几何是「这台机器」的事（`AppPaths` 的原话） |
| `settings.json`（主题）、`shortcuts.json`、`audio-quality.json`、`playback.json`（播放模式 + 记住播放列表）、`volume.json`、`view-mode.json`、`lyrics.json`、`desktop-lyrics.json`、`input-method.json` | 「这个人怎么用这个软件」。换个账号就得重设主题和快捷键会很烦 |

### 账号级 —— **现在错位的就是这三项**

| 项 | 严重度 | 说明 |
| --- | --- | --- |
| `queue.json` | **明确是 bug** | 换账号后新账号直接继承前一个账号的播放队列，还会以新账号的权限去播放它 |
| `history.json` | 判断题 | 「最近播放」。它记的是「这台机器上听过什么」，但换账号就会看到别人的歌 |
| `search-history.json` | 判断题 | 同理 |

`session.dat` 天然是「当前账号」的，不在讨论范围内。

## 二、目录布局

```
%LOCALAPPDATA%\Bowen\
├── devid.txt                    设备级：不动
├── logs\                        设备级：不动
├── cache\covers\                设备级：不动
├── settings.json 等 9 项        个人级：不动
└── accounts\
    ├── anonymous\               未登录期间产生的历史 / 搜索词
    │   ├── history.json
    │   └── search-history.json
    └── <uid>\
        ├── queue.json
        ├── history.json
        └── search-history.json
```

`<uid>` 用明文数字而不是哈希：uid **不是凭据**（它已经在 `session.dat` 的体系里明文出现），
而可读性直接决定排查时能不能一眼看出是哪个账号。

## 三、为什么这不是"加个目录"就完事

三个 store 的路径都是**构造时定死**的：

```csharp
public JsonPlayHistoryStore(string? path = null, ...)   // 默认 AppPaths.PlayHistoryFile
public JsonSearchHistoryStore(string? path = null, ...) // 默认 AppPaths.SearchHistoryFile
private readonly string _path = path ?? AppPaths.PlayQueueFile;
```

而在 `App.xaml.cs` 里它们是 `AddSingleton<IPlayHistoryStore>(...)` ——
**单例 + 构造时定路径 = 永远跟不上账号切换**。

所以必须让路径**在每次读写时按当前账号解析**。三个做法：

| 方案 | 评价 |
| --- | --- |
| **A. store 每次操作时问一次当前账号**（推荐） | 这些 store 本来就是「整体读文件 / 整体写文件」，每次多算一个路径的开销可以忽略。新增一个 `ICurrentAccount` 抽象（只暴露 `Uid`）而不是直接依赖 `BodianSession`，单测里换成假实现即可 |
| B. 账号变更时重建 store | 要处理单例的生命周期与换出时的收尾（历史没落盘怎么办），复杂度明显更高 |
| C. store 接一个 `Func<string>` 路径提供者 | 本质是 A，只是把「问谁」摊给了组合根，反而更散 |

推荐 A。`ICurrentAccount` 只有 `string Uid { get; }`（未登录时返回 `-1`，与 `BodianSession.AnonymousUid` 一致）。

**实际落地时队列走了另一条路。** 历史与搜索历史确实是"每次操作问一次当前账号"，但队列不行：
它的内存副本由 `PlaybackCoordinator` 长期持有，而且落盘是 1 秒防抖的。
切号那一刻协调器手上那份快照属于**上一个**账号，而"当前是谁"已经是新账号了 ——
让 store 自己去问，就会把上一个账号的队列写进新账号的目录。
所以 `IPlayQueueSnapshotStore` 改成显式传作用域（`Load(scope)` / `Save(scope, snapshot)`），
协调器记住"内存里这份属于哪个作用域"，切号时先写回旧的那个。见第五节末尾。

## 四、未登录时写哪儿

历史与搜索词**在未登录时也会被写**（播放历史由 `PlaybackCoordinator` 记，不分登录状态），
所以必须有一个 `anonymous` 桶，不能假设"一定有账号"。

**登录后要不要把 anonymous 那份并进账号？推荐不要。** 合并等于把「用户还没登录时听的歌」
记到一个他当时并未使用的账号名下，这个归属是编出来的。分开存虽然会让用户觉得
"刚登录时最近播放是空的"，但那个行为是可预测、可解释的。

## 五、现有数据怎么迁

三个文件现在平铺在根目录，归属是**读 `session.dat` 才确定的那个账号**：

- 有会话 → 搬进 `accounts/<uid>/`；
- 无会话 → 搬进 `accounts/anonymous/`。

**这里要吸取改名那次迁移的教训。** 2026-10-08 的目录改名带了一次性迁移，
在本机验证成功后代码就删掉了（见 `docs/roadmap.md` 的命名更正一节）——
那次的代价是「从旧版本升级上来的用户会拿到新设备标识」，只是当时判断可以接受。

这次搬的是**用户可见的数据**（队列与最近播放），影响面更大。两个选择：

| 做法 | 评价 |
| --- | --- |
| 带迁移代码，且**保留到确定没有旧数据为止** | 稳妥。代价是几十行 + 一个"什么时候能删"的判断 |
| 不带，本机手工搬一次 | 只有本机一个用户时最省事，但一旦有别人用就丢了数据 |

**已选第一种**，而且这次**不当天删** —— 删之前先确认没有别的机器／别的副本还在跑旧布局。

实现上是 `AccountDataMigration.Run`：**直接读 `session.dat` 定归属**，而不是等会话恢复完成。
会话恢复发生在主窗口首次布局之后，比它晚，而队列在那之前就已经被读进内存了；
直接读凭据可以在"谁都没开始读数据"之前跑完。调用点因此必须在解析 `MainWindow` 之前
（见 `App.OnLaunched`）。目标文件已存在时不覆盖、也不删旧文件，只记一条日志。


## 六、存储页（清理）要跟着改

`StorageMaintenanceService` 现在按 `StorageItemKind` 统计与清理，没有账号维度。加了账号目录后：

- **清理**：只清当前账号那三份。跨账号清用户没选择过的账号数据，是比"清不干净"严重得多的问题。
- **统计**：也只算当前账号的，并在行文案里写明「（当前账号）」——
  否则用户会看到"最近播放 0 B"却清不掉别的账号占的空间，那种不一致比数字小更让人困惑。

## 七、开放问题

| # | 问题 | 当前倾向 |
| --- | --- | --- |
| 1 | 历史到底算账号还是算机器？它记的本意是"这台机器听过什么" | 算账号。换账号还看到别人的最近播放，比"这台机器听过"更让人觉得错 |
| 2 | 队列算账号还是算"这个人的播放会话"？ | 算账号。队列里的歌会以当前账号的权限播放 |
| 3 | 切账号时要不要提示「播放队列已切换」？ | 要（已实现）。队列在界面上是持续可见的，静默换掉会让人以为丢了。正在播的曲目一并停掉 —— 它属于上一个账号，用新账号的权限接着播可能被拒或降级。**启动时恢复会话不弹**：那一次换出的是空队列 |
| 4 | `accounts/<uid>` 用明文 uid 会不会有隐私顾虑？ | 不会。uid 不是凭据，`session.dat` 里本来就有 |
| 5 | 要不要顺便支持"同一个账号在两台机器上"？ | 不在本次范围。`devid.txt` 是设备级的，换机器本来就是新设备 |

## 八、验收清单（实现后）

1. 账号 A 登录 → 听几首歌 → 队列与最近播放有内容。
2. 登出，账号 B 登录 → **队列为空、最近播放为空、搜索历史为空**。
3. 登出，账号 A 重新登录 → 队列、最近播放、搜索历史**原样回来**。
4. 登出状态听几首歌 → 进匿名桶；再登录账号 A 时**不并进** A 的历史（最近播放仍是 A 自己那份）。
5. 主题、快捷键、窗口位置、音质、播放模式**跨账号保持**（这些本来就该共用）。
6. `devid.txt` **全程不变**（这是整个设计里最重要的一条）。
7. 存储页清理「播放记录」只影响当前账号；账号 B 的记录不受影响。
8. 磁盘上看：`accounts\<A 的 uid>\` 与 `accounts\<B 的 uid>\` 各自独立。
