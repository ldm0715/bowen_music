# 歌曲列表工具栏、多选与批量操作

2026-10-04。

在此之前，八个歌曲列表页共用一个隐式行为：**点任意一首歌，整个列表都被替换进播放队列**。
用户只是想听一首，队列却被塞进 177 首。同时列表级操作散落各处 —— 播放全部在页头、
重新加载在左下角页脚、加入队列只能靠行尾菜单一首首点、没有多选。

这一轮把列表级操作收敛到**页面右侧一条工具栏**，并改了播放语义。

## 1. 播放语义：点单曲 = 插到正在播那首的后面并播放

`PlaybackCoordinator.EnqueueAndPlayAsync(track)`：

```
IndexOfQueueItem(track.Id)    // 队列里已有同一首？按 Id 找
  ├─ 有  → Queue.MoveToItem(那一份)      // 不重复添加，直接跳过去播
  └─ 无  → Queue.InsertNext(track)       // 插到当前曲目之后
           Queue.MoveToItem(当前 + 1)     // 游标移过去（空队列时 InsertNext 已落好，不用移）
PlayCurrentAsync()            // 播它
```

- **队列里原有的歌一首都不动。** 之前是 `Queue.Replace(整个列表, index)`，那会把用户攒的队列清掉。
- **落点是「当前曲目之后」，不是队尾**（2026-10-05 改，见 [`play-queue.md`](play-queue.md) §11）。
  排到队尾的话，正在播这首后面原本排着的歌被整段跳过去，点的那首一放完就撞上 `QueueExhausted`
  （顺序模式），听起来像「点了首歌就断档」。插到当前之后，它顶在下一首的位置、后面整体后移，放完照常往下走。
- **队列里已经有这一首时不重复添加**，跳到原来那一份放 —— 点三次同一首歌不该在队列里出现三份。
  `PlayQueue.Append` 因此改成按 Id 去重并返回 `bool`。这一支**不把它挪到当前之后**：挪了就是替用户重排队列，
  而「已经在队列里」本身说明它早就排好了。
- 与行尾菜单的「下一首播放」用的是同一个落点，区别在**要不要立刻播**：点行会换歌，
  「下一首播放」只排队、当前这首继续放着。去重规则也不同 —— 菜单那条允许同一首排两份。

八个点行入口（`PlaylistTracksViewModel` / `AlbumDetail` / `ArtistDetail` / `BangDetail` /
`AiPlaylist` / `Recent` / `Search` 的 `PlayAsync`）、榜单列表页的预览行、发现页的曲目卡片，
全部走这一个入口。

**`PlayFromAsync`（整表替换并从第 N 首播）保留**，现在只剩两个调用点：歌单详情与专辑详情页头的
「播放全部」。那条是显式的整表播放，与上面这个语义不冲突。

### 1.1 `PlayQueue.AppendRange`

「全部加入播放列表」要一次追加几十上百首，逐条走 `Append` 会让队列面板跟着重建 N 次。
`AppendRange` 合并成一次：按 Id 去重（含批内重复）、跳过 `Id <= 0` 的曲目、**整批只抛一次 `Changed`**。

## 2. 工具栏

`Controls/TrackListToolbar.xaml(.cs)`。两个面互斥，靠 `Visibility` 切：

```
普通态  左      共 N 首（或空列表说明 / 「加载失败：…」）
        右      全部加入播放列表 · 多选 · 刷新
多选态  左      加入播放列表 · 加入喜欢 · 加入歌单 · 移出 · 全选 · 已选 N 首
        右      ✕ 退出
```

动作在左、退出在右，是为了让「选完了做什么」和「不选了」在位置上就分得开。

普通态左边那格最初是空的（只有右贴的三颗图标按钮，整行左轻右重），后来把各页页头那行
「数量」挪了进来，见 §2.3。

**选择状态不归工具栏，归 `TrackListView`。** 工具栏只是个遥控器：读 `SelectionCount` 显示计数、
调 `SelectAll()` / `ClearSelection()`、用 `GetSelectedTracks()` 取选中项。
校验一下状态归属：选择必须和「哪些行勾上了」严格一致，而只有列表知道行的事，
工具栏再存一份就是两个真值来源。

页面绑的一样是这几个：`Target`（那一页的 `TrackListView`）、`ReloadCommand`、
`SummaryText`（左上那行文案，见 §2.3），以及可选的两个 ——
`RemovablePlaylistId` / `IsLikedPlaylist`（见 §4.3）。

**服务走 App 资源键 `BodianTrackActions`**，与 `TrackMoreButton` 共用同一个
`TrackActionsService` 实例。本控件是 XAML 实例化的，构造函数必须无参、拿不到 DI 容器 ——
与 `TrackListView.NowPlaying` 是同一处例外。取不到服务就把批量区整个收起来，
**不留点不动的按钮**。

### 2.1 铺在哪八页

歌单详情、专辑详情、我喜欢的、最近播放、艺人详情（歌曲页签）、榜单详情、AI 歌单、
搜索（歌曲页签，跟随 `IsTrackTab` 显隐）。

工具栏统一占**列表正上方独占的一行**。八个页面的头部结构差异太大，只有这样才能保证多选态
左动作栏拿到完整宽度。代价是每页多约 36 DIP 的纵向空间。

### 2.2 左上那行文案：`SummaryText`

`SummaryText`（string DP）收的是**整段文字，不是数字**。口径各页不同，工具栏不该懂业务，
所以由页面拼好给它：正常时是「共 N 首」，列表为空时是空列表说明，加载失败时是「加载失败：…」。
空串表示不占位。

**为什么要管线到工具栏，而不是留在页头**：八个页面原来各自在页头显示数量，位置分两种
（和标题挤在一行的三页、独占工具栏上一整行的歌手页、藏在副标题里的专辑与歌单页），
措辞还有 `N 首` / `N 项` / `N 条` 三种。统一成一处之后，一屏只有一个数字，措辞也统一成「共 N 首」
（对齐播放队列侧栏 `PlayQueueViewModel.CountText` 的旧写法，收敛点在 `Formats.TrackCount`）。

**数量从哪来**，分两种口径：

| 页面 | 口径 | 来源 |
| --- | --- | --- |
| 专辑详情、歌单详情 | **服务端总数** | `Album.MusicCount` / `Playlist.MusicCount` |
| 榜单详情、歌手歌曲、最近播放、我喜欢的、AI 歌单、搜索 | 已加载条数 | `PagedList.StatusText` / 各页 `StatusText` |

专辑与歌单用服务端总数是**沿用**：那个数原来就在页头副标题里（`11 首` / `177 首`），
首屏只拉回一页时它照样是全量。改成已加载条数会让数字从 177 掉到 50，是看得见的回归。
代价是它可能大于实际可播行数（服务端会省略不可播条目，见 `PagedList` 里那条注释）。

**但三种情况必须让位给状态文案**：歌单不存在、首屏加载失败、一条都没拉到 ——
那时「这个歌单不存在」「加载失败：…」「还没有歌」是屏幕上唯一的说明，
报一个总数只会让人以为内容丢了。

**`PagedList<T>` 加的是可选单位参数 `countUnit`，不是改默认值。** 这个类是泛型，
收藏的专辑/歌单、乐库分类、歌手的专辑页签也用它（显示「N 项」，见 `docs/ui-refresh.md`）。
只有曲目列表传 `countUnit: "首"`，其余保持原样。

> ★ 搜索页的页头状态行**没有**搬走。`SearchViewModel.StatusText` 是「当前选中页签」的状态，
> 综合页签也在用它，而综合页签没有工具栏。所以那是搜索状态行不是计数行：页头说
> 「搜了什么」（歌曲页签下改成了「「kw」的搜索结果」，不再报条数），工具栏只说「有几首」。

> ★ `PlaylistTracksViewModel.StatusText` 里手写「共 N 首」而不用 `Formats.TrackCount` ——
> 本文件被链进 `tests/Bodian.Core.Tests` 离屏编译，而 `Formats.cs` 依赖 WinUI 的 `Visibility`，
> 链不进去。改文案时两处要一起改。

**左侧那格缩进了 `SpaceRowPadding` 的左半（4）。** 曲目行的行内边距就是它，计数因此和
下面的列表内容左对齐 —— 不缩进的话它贴在页面最左边，比列表内容凸出去一小截。
两个控件共用同一份 token，改一处两边一起动。

**样式是 `BodianPageStatusStrong`（14px + 主色），不是页面级小字说明那份。**
最初八页统一用了 `BodianPageStatus`（11px + 次级灰），但歌手详情那两行下面紧挨着列表与卡片，
小字淡灰显得和内容脱节 —— 改成正文重之后，同样的落差在另外七页也存在，于是八页统一成这一份。

（中途为「只改一页」加过一个 `SummaryTextStyle` 依赖属性，全站统一后它没有调用点了，已删。
再加属性前先确认是不是所有页面都要同一个值。）

### 2.3 「全部加入播放列表」只加已加载的

不回头翻页拉全，按钮因此是瞬时的。提示里带上真实条数（「已加入 30 首到播放队列」），
**不让按钮名说成「全部」而实际只加了一屏** —— 这是刻意的取舍：拉全一个 177 首的歌单要多等一两秒，
而用户看到条数就知道自己拿到的是什么。

## 3. 多选

### 3.1 复选框复用序号列

`TrackListView` 的序号列从三态升成四态：**多选 → 复选框** 优先于 起伏条 / 播放键 / 序号。

**不新增列。** 行内列宽写的是字面量（`ColumnDefinition.Width` 是 `GridLength`，
而 token 定义的是 `x:Double`，类型不匹配），新增一列要在 `TrackListView.xaml` 与 `Tokens.xaml`
两处同步；而搜索页与榜单列表页还各有一份**复制出来的**行模板。复用槽位把这些全绕开，
列宽一个数都不用动。

代价：多选时那一列不再显示序号与正在播放指示。可接受。

**复选框是纯显示**（`IsHitTestVisible="False"`）：勾选由整行点击驱动。给它自己接点击的话，
「勾上了但计数没变」这类不一致就有了两个来源。

### 3.2 选择状态存在行对象上

`TrackRow` 加 `IsSelectionMode` / `IsSelected`，`TrackListView` 用
`HashSet<TrackRow> _selected` 存选中的行。

**存行对象而不是曲目 id**：`Id <= 0` 的行（搜索页的性能样本、播放历史重建的 `Track`）
根本没法建键；同一首歌在列表里出现两次时按 id 存会两行一起选中。

> ★ **`OnContainerContentChanging` 里绝不清 `IsSelected`。**
> 它是行（数据对象）的状态，不是容器的 —— 容器去装另一行时 `x:Bind` 自然重读那一行的值，
> 本来就不会串。顺手清一下反而会把滚出视野的勾选全丢掉。
> 这里只照旧清 `IsPointerOver` / `IsMenuOpen`。

### 3.3 `Rebuild` 会丢选择，所以刷新必须先退出多选

`Rebuild()`（非 Add 的集合变更）会换掉全部 `TrackRow`，选择集合里存的旧引用随之失效。
两处配套：

1. **刷新按钮在执行 `ReloadCommand` 前先置 `IsSelectionMode = false`** —— 置 false 会连带清空选择
   （`ApplySelectionMode`），由数据层保证「已选 N 首」不会与实际不符。
2. 分页追加走 `NotifyCollectionChangedAction.Add` 的增量路径，不重建，选择保留。

**「全选」只对已加载的行生效**，之后滚出来的新行保持未选。比「粘性全选」可预期。

## 4. 批量动作

### 4.1 批量写入器

`src/Bodian.Core/Services/PlaylistMusicWriter.cs`。喜欢、加入歌单、移出歌单三条路都落到
`service/playlist/music` 上，只是目标歌单与增/删不同，所以节奏控制与失败统计收在一份。

> ★ **默认逐首，不是分块。** 接口签名收的是 id 列表（`BodianApi` 里限 1–100 首），
> 客户端也确实会把整个列表拼进一个请求 —— 但全仓所有真实调用点传的都是**单元素**列表，
> 官方移动端没有多选，多元素那条路从来没对真实服务端发过。
> 分块若服务端只认第一个 id，症状是**静默少加歌**，用户看不出来；逐首最多是慢，还能统计失败。
>
> **实测确认服务端接受多元素之后再改 `PlaylistMusicWriter.Strategy`。**
> 验证方法：拿三个 id 调一次 `AddPlaylistMusicAsync`，确认三首都进了歌单，而不是只进第一首。

其他约定：

| 行为 | 处理 |
| --- | --- |
| 单首失败 | **继续往下做**，最后汇总「成功 N 首、失败 M 首」。一首不可播不该让剩下的 99 首白做 |
| `InvalidOperationException` | **立刻往上抛**，不再发后面的。它表示未登录或会话中途变了，后面每一首都会同样失败 |
| 取消 | 返回 `Canceled` 与已完成数，**不抛** —— 抛出去那个数字就没了，UI 要拿它说「已取消，成功 N 首」 |
| 进度 | 每处理完一批 `IProgress<BatchProgress>` 报一次，界面显示「正在加入 37/150 首」 |

### 4.2 批量喜欢 / 取消喜欢

`ILikedSongsService.SetLikedManyAsync(musicIds, liked, progress, ct)`。要点全部对齐既有的
单首写：入参去重、剔除非正 id、**与单首写在飞去重共用同一个 `_pending` 集合**、
整批记一个 `Session.Revision` 快照。

- **已经是目标状态的不发请求**：喜欢方向跳过已喜欢的（全选一个已收藏的歌单能省掉整批），
  取消方向跳过本来就没喜欢的。
- **有失败或中途换账号就不动本地 `_liked` 集合**，只标脏，交给下一次判定整体重拉。
  半对半错的集合比稍微滞后的集合危险得多。

### 4.3 四个批量动作

| 按钮 | 走哪条路 | 出现在哪 |
| --- | --- | --- |
| 加入播放列表 | `ITrackBatchActions.AddToQueueAsync(选中)` | 所有页 |
| 加入喜欢 | `SetLikedManyAsync(liked: true)` | 所有页 |
| 加入歌单 | 弹窗选目标 → `AddToPlaylistAsync` | 所有页 |
| 移出 | 自建歌单走 `RemoveFromPlaylistAsync`；我喜欢的走 `SetLikedManyAsync(liked: false)` | 只在这两类页 |

**「移出」为什么分两条路**：移出「我喜欢的」本质是取消喜欢，必须走 `LikedSongsService`
才能同步它手里的喜欢状态缓存；直连歌单接口会让爱心图标与服务端长期对不上。
所以「我喜欢的」页面给工具栏传 `IsLikedPlaylist="True"`，自建歌单传 `RemovablePlaylistId`。
两个都为空时这颗按钮整个收起 —— 收藏来的歌单是别人的，移不了。

文案随页面变：自建歌单是「移出歌单」，我喜欢的本质是取消喜欢。

**移出前弹确认框**，默认按钮落在「取消」上（回车不会误触），确认文案带选中数量。
批量移出误点一下就是几十首没了。

**移出完成后退出多选并重取列表** —— 移掉的歌还挂在屏幕上会对不上。

其余三个动作成功后**保留选择**，方便接着做下一个动作（先加喜欢、再加歌单）；退出由 ✕ 显式完成。

### 4.4 歌单选择弹窗

`Controls/BatchPlaylistPicker.xaml(.cs)`，用 `AppDialogs.Create` 包成 `ContentDialog`。

**为什么是对话框而不是浮动面板**：行尾「更多」用 Flyout 是因为它挂在会被回收的行容器里
（二级弹层在那种位置定位不可靠）。工具栏在页面顶层，没有这个约束；而「选一个目标 + 看进度 +
看失败原因」是一屏级的决策，对话框能给它一个稳定的宿主。

**写入过程中不关窗**：失败原因与「已取消，成功 N 首」这类结果要留在面板里，关掉用户就看不见了。
写入时点「取消」是叫停写入而不是关窗。

## 5. 刷新的位置变了

页面**左下角页脚那颗「重新加载」删掉了**，刷新挪到工具栏右上角。
受影响的三页（歌单详情、我喜欢的、艺人详情歌曲页签）页脚现在只剩一个进度环，与其余页同形。

`SearchViewModel` / `RecentViewModel` / `AiPlaylistViewModel` 本轮补了 `ReloadCommand`：

- **搜索页的刷新重跑「已经提交的」关键词**（`_searchedKeyword`），不复用 `SearchCommand` ——
  那个读的是输入框里的 `Keyword`，用户可能改了词还没提交。也**不写搜索历史**（那是 `SearchCommand` 的事），
  页签保持不动。
- **AI 歌单不能直接调 `EnsureLoadedAsync`** 当刷新：它见 `Tracks.Count > 0` 就早退，
  而刷新恰恰是在有内容时按下去的。取数主体抽成 `LoadCoreAsync`，两个入口共调。

封面网格页（收藏的专辑 / 收藏的歌单 / 乐库分类 / 艺人专辑页签）**不迁工具栏**：
它们不是歌曲列表，「点行播放 / 批量喜欢 / 批量入歌单」这套语义对它们没有意义。

## 6. 样式

`Themes/Styles/Pages.xaml` 新增 `BodianIconButton`（28×28、透明底、无边框、`RadiusSm`、
`MinWidth/MinHeight=0`），配套 token `SizeIconButton`。现状已经有四处内联的同一套 Setter，
本轮的工具栏又添了几颗，值得抽。

- 工具栏的「全部加入 / 多选 / 刷新 / ✕」用它 + `FontIcon`。
- 「加入播放列表 / 加入喜欢 / 加入歌单 / 移出」用**默认 Button + 横向 StackPanel**，
  与「收藏 / 分享」同形。**不用 `AccentButtonStyle`** —— 强调色留给页面自己的主操作，
  批量动作是次要动作。
- 图标码位：`E8FD` BulletedList（播放队列）、`EB51` 心形、`E710` 加号（歌单）、
  `E74D` 删除（移出）、`E762` MultiSelect、`E72C` 刷新、`E711` ✕。

**已知取舍**：多选态左动作区有六个部件（四个动作 + 全选 + 计数），窗口拉窄时会挤。
真挤了优先考虑把「全选」换成图标按钮，或把「移出」收进行尾「更多」。
