## 二、关键问题是怎么解决的

### 2.1 协议面（P0）

| 问题 | 结论 |
| --- | --- |
| **签名到底校不校** | **由 `ver` 头控制**：`≤3.0.0` 完全不校验，`≥3.5` 强制校验。本项目钉死 `1.1.7`，播放链路不依赖签名正确 |
| **无损到底能不能拿** | 能。**明文天花板 = 无损 FLAC**（24bit/44.1kHz，`ffprobe` 核实）；Hi-Res 实测拿不到 |
| **音源参数照文档写却降级** | `audioUrl` 的 `format=flac` 会让服务端**静默降级到 mp3**。文档里那条是错的，实测推翻 |
| **`paytagindex` 是什么** | 全工程搜：**客户端零消费**。原「用它推断账号权限」的待办作废 |
| **`freeSign` 从哪来** | **不是签发接口给的**，是服务端在 `payInfo` 里下发的字段，客户端只透传（这解释了为什么一直找不到签发接口） |
| **移动端签名算法** | 用 `blutter` 从 Dart AOT 静态读出（`HttpUtils::encryptParam`，名字有误导性——它是签名不是加密）。**GET 不签名**；移动端排序串覆盖整条 URL 的字母数字，桌面端只签 query —— 这就是 `439` 的根因 |
| **评论接口** | 只服务移动端；换移动端 `ver` 就进入强制签名区间 → **P8 的前置是移动端签名算法的实测验证**，不是参数待探 |

### 2.2 工程面（P1 / P2）

- **`Bodian.Core` 不带 `-windows` TFM** 是关键决策：协议、签名、歌词解码全部可纯单测，不依赖 UI 线程。代价是任何 Windows-only API 都会撞 CA1416 —— 解决办法是把实现挪到 WinUI 层，**不是**给整个 Core 加 `NoWarn`（那会让平台中立的代码悄悄依赖 Windows）。
- **DI 必须显式注册到抽象类型**：`CreateHandler` 返回的是 `SocketsHttpHandler` 这个具体类型，按它注册就解析不到 `HttpMessageHandler`。这个错在 P1 埋下、P2 第一次真正用传输层才暴露（P1 的组合根从不解析 `IBodianTransport`）。
- **播放引擎的三条实测坑**：见 §三 B。

### 2.3 歌词（P4）

- **P1 已经写完了解码链的一半**（`BuildRequestUri` + 一次 Base64、`[kuwo:N]` 八进制系数与 `DecodeWord`），P4 只补了行解析、模型、门面与缓存 —— **先查清已有资产再估工作量**，这一阶段比 roadmap 估的 3–5 天小得多。
- **版式要按 `lrc_info` 分流，不在解析器里猜默认值**：无 `[kuwo:]` 标签不是异常边界，而是 `lrcx=0` 的正常形态。
- **逐字时间是相对行首的偏移**（实证：63 行首词 start 全为 0），不是绝对时间。

### 2.4 系统媒体控件（P3）

- **桌面端没有官方的 SMTC 注册途径**（`GetForCurrentView` 必抛、`ISystemMediaTransportControlsInterop` 在 C# 投影里是 protected、微软 `not_planned`）。**唯一可行入口是借壳**：造一个不参与播放的 `MediaPlayer`，`CommandManager.IsEnabled = false`，再从它取 `SystemMediaTransportControls`。
- **unpackaged 应用的面板名字与图标来自开始菜单快捷方式**，不是 exe。要用 `IShellLinkW` + `IPropertyStore` 写 `PKEY_AppUserModel_ID`（`WScript.Shell` 写不了属性存储）。
- **封面的 webp 问题不用转码**：酷我 CDN 按需生成格式，同一路径换 `.jpg` 后缀即可。

## 三、经验教训

### A. 方法学（最值钱的三条）

1. **先 spike 再实现，错的方案要在半天内证伪。**
   SMTC 借壳是全项目唯一没有官方支持的环节。先写一个 `BODIAN_SMTC_SPIKE=1` 门控的假数据段（几十行），用音量键浮层验证「会话能不能被 shell 认到」，通过后才写正式实现。**这条把「可能整个阶段作废」的风险压到了半天。**

2. **回读验证：让另一方把它看到的说出来，而不是「我看应该对了」。**
   本轮反复用到：写 `.lnk` 后用 `Get-StartApps` 核对 AppID；报 SMTC 后用 `GlobalSystemMediaTransportControlsSessionManager` 把系统侧看到的元数据/状态/时间轴/封面字节数打进日志。
   **「浮层没有进度条」就是这样定性的** —— 回读显示时间轴一直在正常上报（`0:00:00–0:04:40`），所以那不是缺陷，是 Win10 的浮层不画 seek 条。

3. **外部事实先核实，别按想象排期。**
   立项动机里写着「让 Lyricify 能显示歌词」，一度以为必须先做歌词数据层。核实后发现：**Lyricify 自己搜歌词**（SMTC 里没有歌词字段，也没有任何接口能喂给它），所以 P3 与 P4 互不为前置。差一点按错误前提把两个阶段串成串行。
   **反过来也成立**：`Lyricify 4` 只支持 Spotify、不读 SMTC —— 验收对象必须是 `Lyricify Fusion`，这一条不核实就会拿错工具验错对象。

4. **照搬参考实现必须有证据，不能因为「它有名字」就信。**
   `docs/lyrics-ui.md` 曾把参考实现的「长度 < 6 的行跳过」列进待实现清单。实测：那会把 `词：周杰伦`/`曲：周杰伦`/`鼓：陈柏州` 三行真实歌词删掉（63 行 → 60 行）。**现在测试里有一条守门用例**，谁把它加回来就会挂。

### B. 平台与互操作

| 坑 | 症状 | 根因 / 处置 |
| --- | --- | --- |
| `PROPVARIANT` 用显式布局 struct 接 `out` 参数 | `vt` 读出来不是 31 → 每次启动都判定「快捷方式缺 AUMID」而重写 | **编组回来的值是坏的**。改用裸内存：`AllocCoTaskMem` + `Marshal.WriteInt16(偏移 0)` / `WriteIntPtr(偏移 8)`（x64）。读写两侧统一 |
| `IPropertyStore` 写属性 | 属性写进去了，`.lnk` 里却没有（`Get-StartApps` 仍显示 exe 路径） | **属性存储是在 `Save` 时序列化进文件的**。顺序必须是 `SetPath` → `Save` → `SetValue`+`Commit` → **再 `Save` 一次** |
| 读 `.lnk` 的属性 | `Load` 之后直接 `GetValue` 拿到空值 | ShellLink 对象上 QI 出来的属性存储是懒加载的。用 **`SHGetPropertyStoreFromParsingName`** |
| `IPersistFile.Load` 不调就读 | 新建的 ShellLink 是空的，`GetPath` 返回空 → 每次重建 | 读之前先 `Load(path, STGM_READ)` |
| 桌面应用拿不到 SMTC | `GetForCurrentView()` 必抛 `Invalid window handle` | 借壳（见 §二 2.4） |
| **Win10 不预装 WebP 编解码器** | 若走 WIC 转码：开发机一直成功，干净 Win10 上静默没图 | **不要在开发机上验证依赖编解码器的方案**（本机恰好装了商店的 WebP Image Extensions）。用 URL 改写绕开 |
| Win10 的媒体浮层不画 seek 条 | 看起来像「时间轴没上报」 | 平台限制。回读确认时间轴正常；要验拖动得换 Win11 或第三方浮层 |
| Win10 上验不了「拖系统进度条」 | `MinSeekTime`/`MaxSeekTime` 的正确性没有 UI 可验 | 已按规范上报（回读可见），但**本机无法端到端验证这一条**，如实记进 backlog |

### C. 并发与生命周期

| 坑 | 症状 | 处置 |
| --- | --- | --- |
| **拿 `TimeSpan.MinValue` 当节流哨兵** | 首次比较算术溢出抛 `OverflowException`，异常从 libmpv 事件循环逃出，**把整个事件分发打死且进程毫无异常迹象**（进度、文件事件全消失） | 用 `TimeSpan?` 表达「还没上报过」。哨兵类型要能表达「空」 |
| 非 UI 线程的事件 | UI 更新跨线程崩 | **所有事件的唯一出口** `Raise(Action)`：`HasThreadAccess ? 直接调 : TryEnqueue`，入队失败记 warning。集中在唯一出口，不靠调用点自觉 |
| DI 单例构造时取 `DispatcherQueue` | 拿到的队列不可靠 | **懒初始化**：构造函数只订阅事件，首次真正需要时（一定在 UI 线程）才取队列、才建资源 |
| SMTC 初始化失败 | 不能让附加功能拖垮播放 | 失败一次即置 `_initFailed` 永不再试；每处调用各自 try/catch，异常不许冒泡回播放链路 |
| `MediaPlayer` 壳被 GC | 会话消失 | 用字段持有引用 |

### D. XAML / `x:Bind`

| 坑 | 症状 | 处置 |
| --- | --- | --- |
| 函数绑定不接受 `Converter` | `WMC1121`（返回 `Boolean` 但目标是 `Visibility`） | 让函数**直接返回目标类型**（如 `Formats.Visible`） |
| `Uri` 不能直接绑 `Image.Source` | 同样 `WMC1121` | 函数绑定转成 `ImageSource`（`Formats.CoverSource`） |
| `AccentButtonStyle` 自带内边距 | 40px 圆按钮里的图标被裁 | 按钮设 `Padding="0"` + `MinWidth="0"`；图标别塞进写死尺寸的容器 |
| 横向 `StackPanel` 不约束子元素宽度 | 长文本没法用省略号截断，会把布局撑开 | 拼成一个字符串配 `TextTrimming`（`Formats.ArtistLine`），或用 `Grid` 的 `*` 列 |
| 忘了设窗口最小尺寸 | 三栏布局被压到一起，"看起来像控件坏了" | 设 `OverlappedPresenter.PreferredMinimumWidth/Height`。**布局问题与控件缺陷的症状很像**，先怀疑约束 |

### E. 测试与环境隔离

- **测试机上的同名会话会污染结论**：官方 PC 端与本客户端同时在跑时，系统里有两个"波点"会话，Lyricify 抓哪个不由我们决定 —— 当时表现成「封面传不过去」，实际是抓错了对象。**验收前先关掉官方客户端。**
- **`fixtures` 与"合成样本"要说清来源**：歌词响应样本是由解码后的 `.lrc` 反向合成的（零请求），在测试文件里写明了这一点，避免后人以为它是真实抓包。
- **不给"浮层看起来对不对"当验收判据**：能用回读数据判定的，就不靠肉眼。

## 四、被推翻 / 作废的结论（别重走）

| 曾经的判断 | 现状 |
| --- | --- |
| 文档说 `format=flac` 就能拿无损 | **错**，会静默降级 mp3。实测值才作数 |
| `paytagindex` 能推断账号权限 | **作废**，客户端零消费点 |
| `freeSign` 有签发接口 | **不存在**，是服务端下发的透传字段 |
| 无 `[kuwo:N]` 标签要「回退普通 LRC 解析」 | 说法本身不成立 —— 那是 `lrcx=0` 的正常形态，按版式分流 |
| 移动端 API 靠"字符串相邻法"或 ADRP xref 能拼出报文 | **两条都走不通**（Dart AOT 不保证字面量相邻；字符串走对象池 `LDR`，不经过 ADRP）。换 `blutter` 才成 |
| 「长度 < 6 的行跳过」是参考实现的好规则 | **错**，会删真实歌词（见 §三 A4） |
| 必须引入 `Lyricify.Lyrics.Helper` 做统一模型 | **不引入**：它不支持 AWLRC（解析仍要自己写），而 Core 开了 `IsAotCompatible` + `TreatWarningsAsErrors`，未标 AOT 的第三方库直接编译失败 |
| 桌面端可以「原生注册」SMTC | **不行**，必须借壳 |
| 老酷我歌词的 zlib + `yeelion` XOR 解密链 | 那是 `f=web` 端点的，波点端点**只需一次 Base64**。搬错是白干一天 |
