# 搜索系统

更新于 2026-10-06。本文描述当前实现；接口实测依据见 [`bodian-api-reference.md`](bodian-api-reference.md) §2.2。

## 入口与悬浮面板

搜索入口位于主窗口标题栏的 `AutoSuggestBox`，未登录时随外壳隐藏。
点击空搜索框或通过键盘切入会显示热榜与历史面板，保持当前页面和搜索框的键盘焦点。
`GotFocus` 只响应当前仍在搜索框内的 `FocusState.Keyboard`；程序分配的焦点不会展开面板。
输入非空关键词时收起面板，改为展示原生联想列表；联想请求有 250ms 防抖，更新输入会取消上一请求。
回车、搜索按钮、联想词、热榜词与历史词共用提交入口，只有提交非空关键词时才进入搜索结果页。

面板上方为搜索热榜，下方为搜索历史。热榜读取 `search/topic/word/list` 的 `hotWord`，
按 `sort` 排序，显示 `key`；不将运营位或外部跳转内容混入热榜。加载失败可点击标题重试。
历史仅记录已提交的关键词，按最近使用排序，忽略大小写去重，上限 20 条。
它以明文 JSON 保存在 `%LOCALAPPDATA%\Bowen\accounts\<uid>\search-history.json`
（2026-10-08 起按账号分目录，见 `multi-account.md`），重启可恢复，支持清空。
保存先写临时文件再替换，读写失败记录日志；坏文件读取按空历史处理，不删除原文件。

面板是根 `ShellRoot` 中最后一层的 `Border`，不是标题栏内部的模态 `Popup`。
定位由搜索框到根布局的变换计算，面板与搜索框左边缘、宽度一致，顶部距搜索框底部 6 DIP，
最大高度受窗口剩余空间限制。背景复用主题浮窗的 `ThemeFlyoutBackground`（实色），
圆角复用 `RadiusMd`。它曾经是 80% 不透明，正文压在页面上发虚，2026-10-04 改成实色
（见 [`ui-refresh.md`](ui-refresh.md) §24）。
打开时不调用 `Focus`，也不创建阻挡搜索框的关闭遮罩。
点击面板和搜索框之外、键盘焦点移出这两个区域、按 Esc 或窗口失活都会关闭；
外部点击不标记为已处理，目标控件仍响应这一次点击。

## 返回与导航

搜索框左侧常驻 32×32 DIP 的返回按钮，与搜索框间距为 8 DIP，垂直居中。
按钮绑定 `INavigationService.CanGoBack`；没有上一级时禁用，未登录时随搜索入口隐藏。
导航服务通过 `INotifyPropertyChanged` 通知返回状态，包括只清空历史、继续显示同一页面实例的换根操作。

提交搜索使用 `Navigate<SearchPage>()` 压栈，保留进入搜索前的页面；在当前搜索页重新提交不会重复压栈。
结果中的歌单、专辑、歌手详情继续压栈，返回时恢复原页面实例及其结果、滚动位置。
侧栏点击仍使用 `NavigateRoot` 清空历史并切换根页，搜索页没有独立侧栏项，侧栏高亮跟随栈底根页。

专辑、歌手、AI 歌单与音乐馆分类页的独立返回按钮已移除，统一由主窗口的 `GoBack()` 处理。
返回前后关闭搜索面板和联想列表，并将焦点放到返回页面的首个可聚焦元素；没有子元素时尝试聚焦页面。
返回期间忽略搜索框的焦点展开事件，避免返回到根页、按钮禁用后焦点转移而唤起搜索面板。
歌词页保留原来的 ↓ 收起按钮作为例外，按钮与普通窗口下的 `Esc` 同样调用主窗口的返回处理；
全屏下的 `Esc` 仍先退出全屏。详情见 [`fullscreen-lyrics.md`](fullscreen-lyrics.md)。

## 默认综合结果与分类 tab

每次新提交都默认选中「综合」，仅请求一次 `search/comprehensive/v2/list?keyword=...`，
不并行补拉分类接口，也不传 `pn` / `rn`。页面有「综合、单曲、歌单、专辑、歌手」五个 tab。

综合接口的 `data.content` 是分节数组，每个对象直接以分类名作为列表键：

| 键 | 展示分类 | 元素 DTO |
| --- | --- | --- |
| `musicpage` | 单曲 | `TrackDto` |
| `songlistpage` | 歌单 | `SearchPlaylistDto` |
| `artistpage` | 歌手 | `SearchArtistDto` |
| `albumpage` | 专辑 | `AlbumDto` |

只显示接口实际返回的四类音乐数据，保持分节顺序和条目顺序；缺失或空的分类不显示标题。
`interestpage` 直达卡片与 `userpage` 用户信息不属于本次展示范围，解析时忽略。
每个非空分段都有「更多」，点击后选中对应分类 tab，以当前已提交的关键词请求分类首页。
综合结果不分页；分类 tab 才分页，滚到列表末尾自动续加载。

**页签条是 `Controls/PillTabBar`**（2026-10-03 起），不再是 `Pivot`：后者默认模板带下划线指示条、
滑动动画与可拖动表头，与外壳侧栏那套选中语言不是一套。五个页签的内容**全部留在可视树上，只切
`Visibility`** —— 折叠的元素不进布局，容器不会被实现，所以未选中的列表不会跟着自动翻页
（自动翻页挂在「末尾容器被实现」上，见 [`list-paging.md`](list-paging.md)）；
来回切页签时滚动位置也不会再丢（`Pivot` 会整个卸载内容）。控件本身的取舍见
[`ui-refresh.md`](ui-refresh.md) §16.1。

分类搜索分别调用 `search/music/list`、`search/playlist/list`、`search/album/list`、`search/artist/list`。
页号从 0 开始，显式传 `rn`，每次按请求页边界推进；空页结束，不根据 `total` 或短页推算终点。
单曲列表的 `total` 实测恒等于 `rn`；其他分类有总数，但分页仍统一由游标控制。
续加载使用已提交的关键词，输入框里的未提交文本不会改变当前结果或下一页参数。
新搜索、切换 tab 会取消旧请求，旧响应不得追加到新的结果列表。

## 结果工具栏与视图切换（2026-10-06）

「歌单 / 专辑 / 歌手」三个页签上方各有一条工具栏：**左侧是当前页签的结果条数，右侧一颗视图切换按钮**。
排法与单曲页签那条 `TrackListToolbar` 刻意一致 —— 左计数用同一个 `BodianPageStatusStrong`
样式配同一份 `SpaceRowPadding` 内边距（所以四个页签切来切去，那行数字不会换位置），右端图标按钮用
`BodianIconButton`。但它**不是**那个控件：`TrackListToolbar` 的多选与批量入队对这三类结果没有意义，
这里是一条自理的轻量工具栏。这也**不与** [`track-list-toolbar.md`](track-list-toolbar.md) 里
「封面网格页不迁工具栏」那条决定冲突 —— 那条说的是带多选的曲目工具栏。

计数口径是**已加载条数**（与其余页签一致），文案「共 N 个歌单 / 张专辑 / 位歌手」，0 时留空。
**页头那行不再报任何页签的条数**，只写「「关键词」的搜索结果」：单曲页签的条数在它自己的工具栏上，
其余三个在这里，两边都报就是同屏两个数字。

列表与封面网格两态**都留在可视树上、只切 `Visibility`**，显隐是「是哪个页签」× 「列表还是网格」
两个布尔相与（`Formats.VisibleBoth`，因为 `x:Bind` 的函数绑定不能套函数）。这沿用本页既有的规矩：
折叠的元素不进布局、容器不被实现，而自动翻页挂在「末尾容器被实现」上，所以同一份集合喂给两个控件
也不会被触发两遍。网格沿用乐库分类页的专辑卡样式（`BodianCoverCardItem` + `CoverCardLayout`，
封面 132、单元格 144×210）；歌手卡是 `PersonPicture` 圆形头像 + 姓名，**不显示歌曲数与专辑数**。

> ★ 三个网格的 `ItemsWrapGrid.ItemWidth/ItemHeight` 写的是字面量 `144 / 210`，**必须与
> `CoverCardLayout.CoverSize="132"` / `TextHeight="60"` 推出来的值一致**。`CoverCardLayout` 只在
> `Loaded` 与集合变化时算一次尺寸，而这三个网格在页签未选中时是折叠的、那一刻 `ItemsPanelRoot`
> 还是 null，这次重算会整个漏掉 —— 好在它算的是常量（与可用宽度无关），初值写对结果就一样。
> 改封面尺寸时这两处要一起改。

**这个开关不属于搜索页**，见下一节。

## 「行列表 / 封面卡片」这一个开关（2026-10-06）

它管的是**所有「一屏多条封面、靠封面认东西」的地方**，目前六处：搜索结果的歌单 / 专辑 / 歌手三个页签、
「收藏的专辑」、「收藏的歌单」、「关注的歌手」。曲目表格（单曲、歌单详情、专辑详情那些）不受影响。

**全局共用一个开关**，不按页面各记一份：它是「这个人习惯怎么看东西」，不是「专辑这一类结果天生该怎么排」。
按页面分开的话，用户在一处切了卡片、换一处又是列表，只会觉得这个开关没生效。
状态因此放在一个单例 `ViewModeService`（`ViewModels/ViewModeService.cs`）里，页面 ViewModel 只是把它
透给 XAML（`ViewModel.ViewMode.UseGrid`）—— 存多份就要同步，而搜索页的 ViewModel 恰恰是单例、活得更久，
漏一处就是「在收藏页切了卡片、回搜索页还是列表」。

选择落在 `%LOCALAPPDATA%\Bowen\view-mode.json`（`ViewModeSettings`，路径见 `AppPaths.ViewModeFile`），
与关键词历史分开存（一个是内容、一个是界面偏好）。`ViewModeService` 构造时**同步**读一次 ——
晚一帧就会先铺一遍行列表再翻成卡片；用户改一次写一次，构造时读进来的那一次不回写。
写失败只记日志：本次会话的选择已经生效，不该为此报错。

收藏那两页与「关注的歌手」页的用法见 [`collect-follow.md`](collect-follow.md) § 2026-10-06 卡片视图
与 § 2026-10-06 关注歌手列表页。

## 结果交互与字段映射

单曲沿用共享 `TrackListView`。**点单曲一律是「把这一首追加到播放队列队尾并立即播它」** ——
综合页签与单曲页签同一条规矩，不再按所在页签取不同的队列（2026-10-04 改，见
[`track-list-toolbar.md`](track-list-toolbar.md) §1）。单曲页签上方有列表工具栏，
多选、批量入队、批量加歌单都在那里。
歌单点击进入现有歌单详情，专辑进入现有专辑详情，歌手进入新歌手作品页。
歌手作品页提供歌曲、专辑、介绍三个页签，专辑按需加载、分页，并跳转专辑详情；
「重新加载」现在只剩专辑页签一颗，歌曲页签的已挪到工具栏。

搜索歌单使用 `id` / `musicnum` / `source`，与详情的 `musicCount` / `sourceType` 不同，
因此使用独立 DTO；返回的 `source` 原样传入歌单详情和曲目请求，避免静默空歌单。
专辑兼容 `albumId` 与 `id`，歌手读取 `artistId` / `songNum` / `albumNum`。
所有新增响应类型登记在源生成 JSON 上下文，不依赖反射反序列化。
搜索、联想、热榜、综合及歌手作品请求按已验证的公开接口发送，不附加签名。
播放继续经过现有服务端权限检查。

共享 `PagedList<T>` 增加可选分页约定：默认从 1 开始，只有 `search/*/list` 用 0 基。

> ⚠️ **2026-10-03 更正**：这一处原先写的是「歌手歌曲、歌手专辑及专辑详情曲目明确选择从 0 开始」，
> 那是**错的**。实测这三个 `service` 接口都用 **1 基**（`pn=1` 是第 1 页、`pn=2` 是第 2 页），
> 而 `pn=0` 不报错、被服务端当成第 1 页 —— 于是 0 基在首屏看不出问题，
> 游标推进后发 `pn=1` 拿回的还是第 1 页，列表当场翻倍（歌手专辑页 28 张显示成 56 张）。
> 三个调用点都已改成 `OneBased`，实测对照表与判断方法见
> [`bodian-api-reference.md`](bodian-api-reference.md) §1.6。

## 列表图片加载（2026-10-06）

歌单与歌手列表统一通过 `Formats.CoverSource` → `CoverImageCache` 加载图片。
列表和详情接口的图片地址可能不同；歌单 `95020219` 的搜索封面在腾讯图床返回 404，
而详情封面正常。歌单 `2867496601` 的酷我 `_o.jpg` 则可直接加载，后缀不作全局替换。

酷我歌手头像按 `/star/starheads/256/` 请求缩略图，避免 YOASOBI 列表原地址指向约 6 MB 的原图。
网络失败时最多尝试一次已知备用地址；彻底失败的位图移出缓存，再次绑定时可重新请求。
图床限制、原地址回退与验证记录见 [`settings.md`](settings.md) §4.6、§8。
