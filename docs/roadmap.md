## 排序原则

按**风险消除**排序，不按功能顺手排序。确定性工作和不确定性工作混在一起时，先做确定性的会在最后被一个「协议复现不了」整个炸掉。

不确定性，按杀伤力排：

| # | 不确定性 | 如果失败会怎样 |
| --- | --- | --- |
| 1 | 能否复现带签名的 `GET + JSON body`，拿到可用音源 | **项目死亡**。播放是全部功能的地基 |
| 2 | 评论接口参数的具体取值（只有候选名） | 少一个功能，可降级 |
| 3 | 收藏写入参数（无任何静态线索） | 少一个功能，可降级 |
| 4 | `freeSign` 从哪来（见 P0 第 8 项） | 影响免费听场景，可能不影响主流程 |

所以第 1 项必须在写任何 UI 之前打掉；第 2–4 项应该在**同一个有凭据的会话里**顺手探掉——这是唯一一次成本最低的机会。

## P0 · 协议探针（一次性控制台工具）

**目标**：用你自己的账号，验证整条协议链路能跑通。

> **进度（2026-09-30）**：第 1–7 步 ✅ 完成；第 8 步（`freeSign`）出处已定位到看广告流程，但签发接口未找到。
> **最大的风险点已经打掉**：拿得到无损 FLAC、`ffplay` 能直接解码播出，整条播放链路打通。
> 顺带查出一批文档错误——`duration` 单位、`paytagindex` 语义、登录响应的身份字段、
> 以及**最要命的一条**：`audioUrl` 原来的 `format=flac` 参数值会让服务端静默降级到 mp3。
> **签名问题也定了性**：校验受 `ver` 头控制，`≤3.0.0` 完全不校验、`≥3.5` 强制校验。
> 本项目钉死 `1.1.7`，所以不受影响——但签名实现本身仍是错的，见长期维护表。
> **写操作**：红心往返完整验证通过；收藏写入的 body 字段未解；评论确认阻塞在移动端签名上。
> 详细结论见 `bodian-api-reference.md` 第 10 节。

**不要用 WinUI 做这件事。** 一个控制台程序 + `HttpClient` 就够了。这个工具最后会被丢弃，但它是整个项目最省时间的一步。

**要验证的**（按顺序）：

1. 生成并持久化 `devid`（32 位小写十六进制），构造请求头（参考文档 1.2）
2. 实现签名函数，用公开接口（如 `service/music/info`）验证
3. **`checkRight`**：GET + JSON body + 签名。确认 `status` 返回 3 / 7 / 其他
4. **扫码登录**：`qrCode` → 轮询 → `users/login`。确认 `id`/`uid`/`userInfo` 三者一致
5. **`audioUrl`**：同 `checkRight` 的请求形态。拿到 URL 后**用 ffplay 直接放**，不要写播放器代码
6. 搜索 → 单曲详情，确认响应字段与文档第 6 节一致
7. **歌词**：`mobi.s` 请求 + Base64 解码 + `[kuwo:N]` 系数还原。**只需 Base64 一次解码**——老酷我那套 `tp=content` + zlib + `yeelion` XOR 是另一个端点（`f=web`）的，波点端点不用，别搬错（白干一天）。核对三件事：
   - **逐字时间是「相对行首偏移」还是「绝对值」**。参考实现（`tomakino/LyricProvider`，Apache-2.0，明确支持波点）标注为**相对偏移**，但文档没说清，必须实测
   - **`[kuwo:N]` 要按八进制解析**（`parseInt(N, 8)`）。写错整轨时间全废
   - **无 `[kuwo:N]` 标签时的行为**：文档写「默认 N=11」，参考实现是**直接回退普通 LRC 解析**（不做逐字）。两条必有一条是错的

   > **已实测（2026-09-30）**：三条全有定论，且第三条的问法本身不成立——无标签是 `lrcx=0` 的正常形态。
   > 结论见 `bodian-api-reference.md` 2.6 节，样本见 `fixtures/lyric-228908-lrcx{0,1}.lrc`。
   > **本项目相关的修正**：原计划「无脑请求 `lrcx=1`」是错的，应先看 `lrc_info.lrcx` 决定请求哪一版。
8. **`freeSign` 溯源**（新增，见下方说明）

> **第 2 步放在第 3 步之前**，因为签名是整个协议的地基；签名错了两端都验不了。第 3 步（`checkRight`）是最大风险点，过了它项目就立住了。

### `freeSign` 是个未解的口子

`checkRight` 与 `audioUrl` 都带这个参数，文档给了位置和长度上限，**但没有任何资料说明它从哪来、什么语义**。参考实现的默认值是空串，空串能跑通付费曲目的主流程。

推测它与「看广告免费听」有关——客户端里有 `service/advert/watch`、`play/advert/info`、`play/advert/userType`、`activity/vip/payLibRank`，以及 `playInfo.listen_fragment`（试听片段）。**但这只是推测。**

P0 里花点时间确认：分别用空串和一个已有的免费听场景对比，看 `checkRight` 的 `status` 是否不同。**如果空串就能覆盖主流程，就先用空串，把它记成已知限制。**

### 顺手探掉后续阶段的未知项

此时你已有可用会话，成本最低：

- **评论参数**（P8）：拿 `comments/v3/new` 试 `{musicId, pageNum:1, pageSize:20}`，看返回结构再补 `sortType`/`resourceId`；再试 `publish` / `like` / `replies`
- **收藏写入**（P7）：**往返验证**——一次性临时歌单，`service/collect` 收藏 → `collect/4/list` 确认 → 取消 → 再确认。参数从 `{musicId, playListId, source, type}` 开始试
- **Hi-Res 能不能拿**（决定音质上限）：同一首歌打 `{format:"flac", br:"2000kflac"}` 与 `{format:"flac", br:"4000kflac"}`，比 URL、实际文件大小与采样率
- **`paytagindex` 状态码**：同账号下有 / 无对应权限的两首歌对比取值，把文档 7.3 的推断验成事实
- **下载接口增量**：`service/music/download/{info,config}` 与 `audioUrl` 对比，看有没有更高码率或专用配置

- **真实响应样本存成 fixture**——P1 的单元测试全靠它。**脱敏时必须抹掉**：`token`、`uid`、`freeSign`、audioUrl 里的签名参数、任何账号标识。歌曲名/歌手可以保留

## P1.5 · 透明悬浮窗 spike（新增，一次性验证）

**为什么新增**：协议风险由 P0 解决后，**桌面歌词窗那套「无官方 API 支持的透明 + 点击穿透」成了新的头号风险**。按本文自己的「风险消除优先」原则，它必须提前验证，不能等做到 P6 才发现做不了。

**只验证一件事**：同进程的第二个 `WinUIEx.WindowEx`，在 Win10 19045 上能否同时做到 ① 逐像素透明 ② 置顶 ③ 点击穿透 ④ 可拖动。

**做法**：用一张静态图片或假歌词即可，**不要接真实播放状态**。四个坑的已知解法写在这里，照着试：

- 透明靠**自写一个「画透明色」的 `SystemBackdrop`**（或直接用 `WinUIEx.TransparentTintBackdrop`），不是 Mica/Acrylic
- **不要用 `OverlappedPresenter.IsAlwaysOnTop`——它会破坏点击穿透**。改用每 ~100ms 的 `SetWindowPos(hwnd, HWND_TOPMOST, ..., SWP_NOACTIVATE)` 兜底
- **`WS_EX_TRANSPARENT` 是整窗穿透**，做不到「透明处穿透、文字处可点」。要靠 50–100ms 定时器轮询 `GetCursorPos` + `TransformToVisual(null)` 动态切换
- Win10 上透明窗可能有一条细白边，解法是去掉 `WS_DLGFRAME` 样式位

**产出**：Spike 代码**可丢弃**，结论（能/不能、Win10 上的实际表现）写进 `tech-stack.md`。

**如果这步过不了**，P5/P6 的方案要整个重估——这正是把风险提前的意义。

**工作量**：1–2 天。

## P3 · SMTC + 播放状态

**这一阶段验证项目的原始动机**：让 Lyricify 能读到你的播放状态。

### 方案已改：不能「原生注册」，必须借壳

原计划写的「用 CsWinRT 原生注册」**走不通**：

- `SystemMediaTransportControls.GetForCurrentView()` 在桌面应用**必然抛 `Invalid window handle`**——所有 `XxxForCurrentView` 系列都依赖 `ApplicationView`
- 微软已在 [WindowsAppSDK#127](https://github.com/microsoft/WindowsAppSDK/issues/127) 明确表态并以 **`not_planned`** 关闭：*"no plans for improvements for unpackaged apps without app identity"*
- 官方替代接口 `ISystemMediaTransportControlsInterop` **在 C# 投影里是 protected，拿不到**（C++ 可用）

**正确做法——借壳**：创建一个**不参与实际播放**的 `Windows.Media.Playback.MediaPlayer`，先 `CommandManager.IsEnabled = false`，再从它的 `SystemMediaTransportControls` 属性拿到 SMTC 实例。这是纯 C# 唯一可行入口。

- `ButtonPressed` 事件**不在 UI 线程**，回调必须 `DispatcherQueue.TryEnqueue` 回主线程
- 要报的属性：标题/歌手/专辑/封面（**webp 要转 JPEG，SMTC 不认 webp**）、`TimelineProperties`（进度与时长，可拖动）、播放状态、上一首/下一首/停止
- 封面与进度要跟着走，否则状态栏歌词跟手不上

### unpackaged 下的应用名问题

**SMTC 面板默认显示的是 exe 文件名，不是应用名**。要让名字和图标正确：

- 在 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\` 放一个指向 exe 的**快捷方式**——SMTC 取的是**快捷方式的名字与图标**，exe 自带的无效
- 同时 `SetCurrentProcessExplicitAppUserModelID` 一起做（影响任务栏分组与 toast 归属）

**这条直接影响本阶段验收**——Lyricify 读到的应用名就是它。

**验收**：**Lyricify Fusion 能识别并显示歌词**（它直接读 SMTC）。

> 注意：Folia 不能直接读 SMTC，它通过本机 `now-playing-service` 接入。所以"Folia 能显示歌曲"不是本阶段的直接验收项，要另外部署那个服务，且它是否支持任意 SMTC 源未验证。

**工作量**：中，3–4 天。

## P5 · 主歌词页（逐字渲染）

**这一阶段的成本不在渲染，在文本样式重建。**

- **观感目标已锁定为 BetterLyrics 的歌词样式**（用户明确坚持）。`lyrics-ui.md` 4.1–4.3 已从它的源码里取出实际参数——逐字裁剪机制、默认效果与阈值、Apple Music 式指数错峰滚动曲线。**照着对齐，不要自己重新设计参数**
- 走 **Win2D 路线**：`CanvasAnimatedControl` + `CanvasTextLayout` + `Geometry.CombineWith(Intersect)` 几何求交。这是唯一能做「单字独立裁剪/缩放/上浮/发光」的技术路线（XAML 的 `TextBlock` 没有任何逐字定位 API）
- 必做：逐字扫光高亮、**长音拖尾发光**（仅 ≥700ms 的音节）、长音放大、远景模糊、当前行放大、波浪式滚动
- `BetterLyrics` 的 `Renderer/` 与 `HyPlayer` 的 `LyricRenderer/` **可直接移植**（都是 GPL-3.0）——**本阶段估时是按「移植 + 适配」算的，不是从零写**
- 真实工作量在：**CJK 与西文双字体族的回退**、字距、行高、emoji 彩色字体、`TextTrimming`。这些 `TextBlock` 白送的，Win2D 全要手动对齐

**验收**：与 BetterLyrics 逐字对照，观感一致。

细节见 `lyrics-ui.md` 第 4 节。

**工作量**：中到偏大，1–2 周。

## P6 · 桌面歌词条

- 依赖 P1.5 的 spike 结论。方案：同进程第二个透明 `Window`，与主窗共享 ViewModel，**逐字进度同步零 IPC 成本**
- **先只做纯歌词条**（当前行 + 横向扫光 + 置顶 + 点击穿透 + 可拖动）。跑顺了再考虑扩成带封面和播放控制的迷你播放器
- 歌词条只要横向扫光，走 **XAML 双 `TextBlock` + `RectangleGeometry` 裁剪**即可，**零 Win2D 依赖**，体积小启动快
- 任务栏歌词、壁纸层歌词依赖同一套 Win32 悬浮窗技术，可复用

**不做**：全屏自动隐藏。`WS_EX_TOPMOST` 挡不住独占全屏的 D3D 应用，HotLyric 作者做到一半直接把选项藏了。最多做「检测到全屏就隐藏」的粗粒度降级。

**工作量**：中，4–6 天。

>
> 评论端点只服务移动端。用桌面头（`plat: win` + `ver: 1.1.7`）打 16 个端点，全部返回空数据或服务端异常 —— 服务端不把这种请求当移动端处理。而换移动端的 `ver`，就进入 **`ver ≥ 3.5` 的强制签名校验区间**，本项目对签名算法的实现在那里是**错的**（`439 sign invalid`）。

>
> **建议**：把 P8 从「3–5 天」改标为**阻塞**，不要排在 P7/P9 的同一梯队里。它的估时取决于要不要投入移动端逆向。

## 长期维护（容易被忽略）

| 项 | 说明 |
| --- | --- |
| **协议变更** | 官方 PC 端**当前仍是 1.1.7**（`service/version/check/pc` 用旧版本号查询会返回当前版本号与下载地址），PC 这条线没有动过。**但 `ver` 不是可以随便跟的**——实测 `ver ≥ 3.5` 会触发服务端强制校验签名，而本项目对 1.3 节签名算法的实现在强制校验下是**错的**（十种变体全被拒，`439 sign invalid`）。**跟 `ver` 之前必须先拿到对应版本的客户端并重新推导签名算法**，否则全部请求会一起挂掉，且错误只有一个 `439`。建议保持 `ver=1.1.7`，定期用 `service/version/check/pc` 观察；把「接口变了」的错误处理做成可诊断的，而不是笼统报网络错误 |
| **账号风控** | 用第三方客户端调官方接口，**存在账号被风控的风险**（设备指纹、行为异常）。建议用小号先跑，观察一段时间再上主号。`devid` 必须稳定复用，不要每次启动重生成——频繁变设备标识本身就是异常信号 |
| **请求节流** | 加并发上限与最小间隔，别把别人的服务当压测对象 |
| **fixture 时效** | P0 存的样本会过时。协议变更后要重新采 |
| **Windows App SDK 升级回归** | 桌面歌词窗的透明/点击穿透**走的是没有官方承诺的 hack**（透明窗口的 feature request 开了 7 年仍是 proposal）。**每次升级 WinAppSDK 都要重新验证 P6 的悬浮窗**，别当常规依赖升级处理 |
| **GPL 义务** | 项目是 GPL-3.0。移植第三方代码时逐个文件记来源，仓库需附完整协议文本、保留原作者版权声明、标注改动过的文件。别等发布前再补 |

## 一直要守的线

| 项 | 要求 |
| --- | --- |
| 音源授权 | 完全交给 `checkRight`，没权限就提示用户，不在客户端自行推断 |
| 音质范围 | 见 `bodian-api-reference.md` 第 7 节。**明文天花板 = 无损 FLAC，已实测**；Hi-Res 实测拿不到（请求 `4000kflac` 降级到 128k mp3）；加密容器档位是**待定项**，不由本计划预设 |

| 分发 | 不打包官方客户端的任何二进制（含 `libmpv-2.dll`、图标、文案）——**这条与 license 无关，是另一回事** |
| 许可证 | 本项目 **GPL-3.0**。**GPL-3.0 的第三方代码可直接移植；AGPL-3.0 的不行**（两者是单向兼容的）。完整边界清单见 `lyrics-ui.md` |
| 协议事实 vs 源码 | 只用 `bodian-api-reference.md` 记录的协议事实，**不要拷 `bodian-music-api` / `folia-major` 的源码**（AGPL-3.0——注意即使项目本身是 GPL-3.0，AGPL 代码**仍然不能碰**） |
| 身份声明 | 项目为非官方第三方客户端，仓库与关于页应写明 |

## 明确不要做的

- 本地 HTTP 代理（单进程桌面应用做这个是纯负债）
- P2P 下载（`tp2p` / `libDownloadProxy`）—— 有更简单的替代路径
- 一开始就做 UI（先用 P0 的控制台把协议钉死）
- 追老酷我 Web 接口
- **老酷我歌词端点的 zlib + `yeelion` XOR 解密链**——那是 `f=web` 端点的，波点端点只需 Base64 一次解码。搬错是白干一天
- **同进程同时承载 WinUI 3 和 WPF**（想让歌词窗用 WPF 的捷径）——不受支持，会报 `interface that was marshalled for a different thread`，且加 `<UseWPF>true</UseWPF>` 会静默破坏构建
- **用 Mica/Acrylic 做桌面歌词窗的「透明」**——那是 DWM 材质，给不了「文字浮在桌面上」的效果。要自写画透明色的 backdrop
- **桌面歌词的「全屏自动隐藏」**——`WS_EX_TOPMOST` 挡不住独占全屏的 D3D 应用，这是 OS 层行为。最多做粗粒度降级

## 建议的第一步

P0 的**第 1–3 步**：`devid` + 签名 + `checkRight`。**✅ 已完成（2026-09-30）。**

做完这三步就知道最大的风险点成不成立——`checkRight` 通了，项目立住了。
但第 2 步的「签名」只做到了「服务端接受」，没做到「服务端校验」，**匿名会话下 `sign` 传什么都返回 200**。
所以第 4 步登录不只是为了拿会话，**它同时是签名实现的唯一验证机会**：登录后第一件事就是重跑 `signtest`。

登录一通，搜索 / 播放 / 评论 / 收藏的探测都在同一个会话里顺手做完。

**排在第二位的风险是 P1.5 的透明悬浮窗 spike。** 协议过了之后，整个计划里唯一没有官方保障的就是它。建议 P1 一结束就把它做掉，别往后拖——它的结论会决定 P5/P6 要不要改方案。
