# 应用性能优化与验证（2026-10-02）

2026-10-07：新增的页面、Tab、卡片、共享封面和主题过渡见 [应用动画](animations.md)。主题过渡使用独立合成层，不栅格化整窗、不动画共用主题画刷；本次切换耗时与验证范围单独记录在该文档。

本轮目标是 120 fps（每帧约 8.33 ms），覆盖窗口操作、歌词、频谱、倒影、导航、封面和播放通知。
下面严格区分后台绘制频率、UI 输入响应和屏幕呈现；定时器频率不当作呈现帧率。

## 环境与测量

- Windows 10 22H2，系统版本 19045。
- AMD Ryzen 5 4600H，6 核 / 12 线程；NVIDIA GeForce GTX 1650 Ti。
- 主显示器 2560×1440，驱动报告 200 Hz；窗口处于 125% DPI。
- 使用本机 Release 构建，真实播放「花の塔」的 101 行逐字歌词。
- 重页面使用真实排行榜（20 个榜、124 个分组/榜头/预览条目）及实际搜索模板的一万条本地数据，避免仅测少元素页面。
- 通过 `BODIAN_LYRICS_DIAGNOSTICS=1` 记录绘制耗时、帧间隔、页面和窗口处理时间。
- 拖动/缩放使用物理像素鼠标输入，显式设置测试线程的 DPI 上下文；校验窗口位置/尺寸确实改变。
  随后用 `WM_NULL` 与 `SendMessageTimeout` 测消息响应，并检查页面未被切走。
- 全屏每轮核对窗口确实变成显示器尺寸并恢复原窗口；切换由另一线程触发 UI Automation，同时采样消息响应。
- `MoveWindow(..., repaint: true)` 和 UI Automation 调用本身含同步重绘/自动化等待，其总耗时不等同鼠标输入响应。
- PresentMon 能捕获当前会话的桌面合成及其他交换链，本程序的 CompositionDrawingSurface 没有独立可归属的交换链数据；不能据此宣布整应用实际呈现锁定 120 fps。

## 已确认的原因

### 窗口移动与缩放

采样栈落在 `Microsoft.UI.Input!InputNonClientPointerSourceWinRT::SetRegionRects_Callback`，随后通过
`CalculateUnionRectAndSetWindowPos_Callback` 移动输入辅助窗口。原实现每个窗口位置变化都经过这条路径。
同时歌词在 UI 的 `CompositionTarget.Rendering` 里绘制；宽度或字号变化又使整首歌词排版失效。

`WindowRenderActivity` 在交互或全屏切换期间合并位置变化的输入区域同步，标准窗口过程继续处理
客户区尺寸/位置，在松手或切换结束后把最终状态交给窗口层。最小化、显示/隐藏和销毁保持正常处理。
标题栏停止在每次全局布局更新时递归扫描；交互控件实际变化时主动重算区域。

### 最小化闪退

转储显示窗口层在调用 `AppWindow.Changed` 事件处理器后收到 `E_INVALIDARG`，进入原生 FailFast；
它不会按普通托管未处理异常的形式落日志。最小化也会带来 presenter 变化，旧歌词页回调把它当成
全屏切换，重设标题栏布局与按钮。现在先排除最小化，比较实际全屏状态，并在 COM 事件边界内记异常。

频谱采集器的 `Dispose` 还会等待 WASAPI 采集线程，旧代码在可见性事件里同步释放，也会卡住 UI。
启停现在由一个后台循环根据最新期望状态串行处理；频谱结果以不可变快照发布，UI 不再等待 FFT 或采集锁。

## 最终实现

- 歌词、频谱、倒影使用独立 Composition 表面与后台绘制线程，各自目标 120 Hz；XAML 属性由 UI 发布成输入快照。
- 使用高精度可等待计时器和绝对时间帧调度；长帧后跳过过时帧，不忙等、不全局修改系统计时器分辨率。
- 隐藏、最小化和全屏过渡暂停视觉刷新；普通移动/缩放继续动画，播放引擎、队列和 SMTC 继续运行。
- 整个窗口由 `ResponsiveViewport` 承载。120 Hz 帧预算内的轻布局可以实时提交；
  超预算的页面在连续缩放期间保留布局，逐帧只改合成变换，松手后一次提交准确排列与字号。
  这会暂时缩放现有文字/卡片，避免拖动边框时整树反复重排；不是把画面停在旧尺寸。
- 绘图线程结束后，Composition 对象回到创建它们的 UI 线程释放；设备丢失按同样边界重建。
- 首轮歌词只排整行与测量高度；实际播放到某行时才准备逐字区域和长音资源。缓存最多三份不同尺寸/字号的排版。
- 全屏使用同一个窗口的无边框显示器覆盖，保存 Win32 placement 与样式；退出恢复尺寸、位置及原最大化状态。
  原生样式/位置提交的等待在后台完成，重复全屏点击串行处理；不从绘图线程调用 XAML。
- 模糊封面背景使用固定分辨率缓存，由合成器缩放；隐藏被歌词页遮挡的外壳背景；相同原生按钮配色只提交一次。
- 通过共同的 `VirtualizedListView` 设置可回收面板、半屏预取，并限制无限高度/宽度到窗口视口。
  排行榜平铺到标题、榜头和曲目行；搜索综合页平铺不同结果类型；发现页平铺到每个卡片区。
  同一方向不再套外层 `ScrollViewer` 和内层列表。诊断直接读取实际实现容器，日志带进程 id。
- 搜索分页追加只初始化新增行的播放状态，避免每追加一项就扫描整批结果造成平方级开销。
- 常用根页按类型保留最多八个实例，重复导航优先复用；登录/登出重置时清缓存。
- 封面图片缓存最多 128 个条目、估算解码内存预算 64 MiB，列表设置解码宽度 256 px、主封面 1024 px；先设解码尺寸再请求图片。
  2026-10-06 补充：酷我专辑封面与歌手头像按 CDN 路径请求对应尺寸，避免列表下载大原图；其它路径保持原样。
  网络加载失败时最多尝试一次备用地址，彻底失败的位图移出内存缓存，下次绑定可重试。
  地址规则与两个歌单、YOASOBI 的实测结果见 [`settings.md`](settings.md) §4.6。
  取色使用 60 px JPEG，并在后台读取像素和计算颜色，过期请求会取消和释放。
- 播放进度只保留最新值、最多排一个低优先级 UI 回调，避免窗口繁忙后重放积压通知。
- 发现页返回时重新挂滚动加载监听；卸载时继续解绑。

## 回归范围与限制

Core 回归增加通知合并、布局预算以及页面布局结构的用例，共 604 项通过。
结构回归覆盖排行榜/搜索/发现页不能重新引入外层滚动与整组 `ItemsControl`，
并检查所有页面的垂直列表不能直接放在无界 `StackPanel` 中。
测试不会证明未来任意模板都能锁定 120 fps，但会拦住本轮已确认的虚拟化失效路径。
窗口回归覆盖连续鼠标拖动/缩放、普通窗口/显示器全屏切换、最小化恢复、隐藏期间播放位置推进、
常用侧栏页重复切换和搜索输入。Debug 与 Release 的构建产物都应使用最新补丁。

120 Hz 是动态绘制目标。首帧、换歌、尺寸改变、驱动调度及首次图片资源仍可能出现长帧；
短样本的峰值或稳态不能证明所有页面、每次冷启动和多显示器组合都锁定 120 fps。
静态页面不需要不断重绘；滚动和系统合成以实际显示刷新率运行。

复测脚本与临时结果保存在 `artifacts/window-performance/`（不入版本控制）。
性能诊断默认关闭，只在启动前临时设置环境变量；日志没有添加音源地址或会话凭据。

## 后续页面重设计的性能约束

1. 页面放在既有 `WindowViewport` 下，保留有限视口尺寸，不绕过共同的缩放入口。
2. 单向滚动使用 `VirtualizedListView`；分组标题、行、卡片区作为数据项，模板选择负责显示。
3. 横向卡片使用可回收横向 `ItemsStackPanel`；避免一个虚拟化单位包含任意大的整组子树。
4. 图片走共同缓存，动画走 Composition 或后台绘图，UI 回调只发布输入和显示状态。
5. 重设计必须跑真实页面及大数据场景，比较已创建容器、输入延迟、首帧和稳态帧间隔。

可重复的大数据场景默认关闭，只在本机明确设置以下变量时使用真实搜索页模板：

```powershell
$env:BODIAN_LYRICS_DIAGNOSTICS = '1'
$env:BODIAN_UI_PERF_SCENARIO = 'search-list'
$env:BODIAN_UI_PERF_ITEMS = '10000'
& './src/Bodian.WinUI/bin/Release/net10.0-windows10.0.26100.0/win-x64/Bodian.WinUI.exe'
```

它不请求搜索接口，不写搜索历史，使用负数 id 的本地样本；正常启动没有样本数据。
测试结束后关闭该测试进程，使用未设置这些变量的终端正常运行应用。

## 内存与后台 CPU 优化（2026-10-07）

本轮优先级为内存、CPU 和播放功能。此前的 120 Hz 改造说明是历史实现，
现在滚动动画保留最高 120 Hz，逐字扫光最高 60 Hz，频谱 60 Hz，倒影 30 Hz。
暂停、音节间隙和逐行歌词稳定时保留合成表面，只在画面变化时提交绘制。

确认并处理的资源来源：

- 原生 mpv 回读默认预读上限为 150 MiB、向后缓存 50 MiB，网络预读时间为 3,600,000 秒。
  音乐播放现在限制为前向 16 MiB、向后 4 MiB、预读 60 秒；保留网络缓冲和跳转能力。
- 歌词不再为每个已播放的行永久保留高亮纹理、逐字画刷和长音纹理。
  位图缓存仅保留视口附近，非当前行释放活动资源；换歌释放旧文档排版。
  点击命中区域复用数组，避免每帧按整首歌词行数分配。
- 歌词、频谱和倒影共享一台独立后台 CanvasDevice；最后一个使用者结束后释放，
  仍与 UI 的 CanvasControl 设备分开。最小化和隐藏到托盘释放后台表面、设备及背景视觉，
  恢复时重建；短暂全屏过渡只暂停绘制。
- 播放列表的小条形动画在卸载、被折叠祖先遮挡和主窗口进入后台时停止。
  旧实现没有 Unloaded 收尾，缓存的页面会保留循环动画并持续驱动合成线程。
- 图片内存缓存预算从 64 MiB/128 条改为 16 MiB/48 条；后台清理闲置图片和侧栏根页缓存，
  当前页与返回栈仍保留。模糊背景与倒影分别请求 384 px、512 px 封面。
- MV 播放器与频谱源由页面工厂创建，避免 IDisposable transient 被根 DI 容器保留到退出。
  MV 初次加载会随离场取消；换画质时取消、超时和快速离场都会释放备用播放器及媒体源。
  后台解绑视频呈现宿主，保留播放和试看限制，恢复时重新绑定。

### 同机 Release 对比

旧版在独立的 `artifacts/memory-performance/baseline-20261007` 中从 HEAD 构建，
未回滚工作区；新版使用当前 Release 输出。相同歌曲、窗口尺寸和设置，每项采集 8 个样本，
歌词采集窗口约 16–17 秒；MV 每项 6 个样本，约 13–15 秒。CPU 按 12 个逻辑核归一化；内存采用私有工作集，
与总工作集、提交内存分别记录，不能混用。

| 场景 | 旧版私有工作集 | 新版私有工作集 | 旧版 CPU | 新版 CPU |
| --- | ---: | ---: | ---: | ---: |
| 歌词页播放 | 193.2 MiB | 147.8 MiB | 5.94% | 4.12% |
| 歌词页最小化、音频继续播放 | 192.2 MiB | 135.1 MiB | 1.27% | 0.18% |
| 冷启动后直接播放同一首 720p MV | 175.4 MiB | 155.1 MiB | 1.88% | 0.56% |

这些是本机短时样本，不代表所有硬件或所有音视频的峰值。音频质量、歌词长度、
屏幕 DPI、视频解码器和驱动均会影响结果；WinUI 和媒体框架仍有基础占用。
经历多次全屏、重进页面和换画质之后，新版 MV 的另一轮短时样本约 211 MiB，
因此不能把上述冷启动数字当作内存上限。本轮没有使用强制 GC 或清空工作集来制造数字下降。

原始测量保存在 `artifacts/memory-performance/`（不入版本控制）。复测可在应用进入目标状态后运行：


该脚本只采集目标进程 CPU、私有工作集、总工作集、提交内存、线程与句柄数量，
不主动清理工作集、不控制播放器。需分别在播放、暂停、最小化、托盘隐藏和 MV 场景运行。

验证包括 Core 1420 项通过、Debug/Release 构建，以及 MP3、FLAC、192 kHz FLAC、ALAC
和本地 HTTP MP3 的暂停、seek、恢复、位置事件与播放结束检查。
UI 验证包含三轮歌词全屏/最小化恢复、三轮歌词进出、MV 三档换画质续播、明确退出，
以及最小化/托盘隐藏时播放位置继续推进。托盘测试重新开始音频后，隐藏前位置为 0.53 秒，
恢复时 6.56 秒。UI 验证结果另存于上述 artifacts。

## 主窗口目标：约 100 MiB、常态 CPU 低于 1%（2026-10-07）

本次优先级按用户后续要求转到主窗口。前一节的歌词/MV 数据保留为历史样本，
不能用它代替本次主窗口验证。普通播放页、暂停和隐藏测量期间均不进行 UI 自动化操作。

### 本次修改

- 氛围背景保留封面配色和三团柔和光晕，预绘成 384×256 的 BGRA 小图。
  不再常驻全窗口渐变效果及永久漂移动画；换歌重新取色，窗口缩放复用像素。
- 封面取色改用 `BitmapDecoder` 的 CPU 解码，保留 JPEG 地址改写、取消和过期响应检查，
  不再为了 60×60 的图片建立 Win2D 共享 D3D 设备。
- 当前曲目的三根标记与真实播放状态同步，暂停时保留静态标记。
  多处标记共用一个 20 Hz 时钟，只改合成缩放、不改布局；不可见时完全停止。
  原先标记绑定的是 `IsCurrent`，暂停后仍运行永久动画，是暂停 CPU 偏高的来源之一。
- 128 px 列表封面与头像足够覆盖当前行的物理显示尺寸；头像复用缓存，不再每次属性读取创建原图。
  常规播放封面使用 256 px，进入歌词页升到 1024 px，退出后降回并移出大图缓存。
- 图片 LRU 预算继续收紧为 8 MiB；常用根页缓存最多三页。主窗口与小窗的队列内容按需创建，
  关闭后释放控件与行容器，队列数据仍由同一 ViewModel 管理。
- 窗口是否绘制直接由 `WM_SHOWWINDOW` 和最小化消息跟踪。隐藏到托盘时在原生消息阶段暂停视觉刷新，
  不依赖事件期间可能尚未同步的 `AppWindow.IsVisible`。
  播放标记的暂停状态按 `XamlRoot` 分开，主窗口隐藏不会停掉可见小窗的标记。

桌面歌词与小窗同时保留本轮已完成的修正：按歌词时间轴等待，逐字/长句最大 60 Hz；
隐藏时停绑定和监听，桌面歌词释放绘图资源，小窗按实际尺寸解码封面。
鼠标远离时轮询为 100 ms，进入交互区时回到 30 ms，拖动与贴边唤醒保持原有入口。

### 正式产物的 30 秒测量

使用正式 `src/Bodian.WinUI/bin/Release/.../Bodian.WinUI.exe`，同一歌曲与普通“我喜欢的”页。
桌面歌词与小窗未创建，实际采集时不切页、不切主题、不滚动，也不同时编译。
CPU 按 12 个逻辑核归一化，逐秒记录；内存为采样结束时的私有工作集。

| 场景 | 采样时间 | 平均 CPU | 最高一秒 CPU | 私有工作集 |
| --- | ---: | ---: | ---: | ---: |
| 普通主窗口播放 | 30.67 s | 0.637% | 1.145% | 106.6 MiB |
| 普通主窗口暂停 | 30.58 s | 0.068% | 0.258% | 108.0 MiB |

这是“约 100 MiB、常态平均低于 1%”的验证，不能写成所有瞬时样本都低于 1%，
也不能写成所有页面都严格少于 100 MiB。总工作集还包括共享的框架/模块页：
播放样本总工作集 262.5 MiB，私有提交 179.4 MiB，与私有工作集不是同一个指标。
歌词、MV、首次加载和持续浏览的数据量会增加额外资源，需另外测量。

在相同未创建浮窗条件下，改动前的独立 Release 样本：普通播放 5.44% CPU、116.1 MiB，
暂停 5.23% CPU、118.8 MiB。初期创建过桌面歌词后关闭的样本约 140 MiB，
它不能直接和“未创建任何浮窗”的 106.6 MiB 当成相同条件比较。

原始逐秒数据和函数验证结果保存在 `artifacts/main-performance/`，悬浮窗样本保存在
`artifacts/overlay-performance/`，均不入版本控制。`dotnet-counters` 回读显示，
一个中间版本的托管存活堆约 10 MiB、GC 提交约 20 MiB；剩余内存并非只靠减 C# 集合就能消除。
实验性的 GC 节省模式没有明显收益，未写入正式配置。
没有使用强制 GC、工作集清空或降低音质制造数字下降。

Core 回归 1434 项通过；Debug/Release 正式构建均通过。
本轮没有把物理拖动/拉伸测试未完成的部分写成验证通过；后续优先验证主窗口功能与占用。

### 连续浏览仍未达到内存目标

对八次页面切换、两次主题切换、三次队列打开/关闭和歌词进出继续复测。
发现原生定时器只 Stop 不退订回调的路径，已经修正歌词页、音量入口、列表诊断、
缩放视口与共享封面等待回调；歌词背景独立设备在卸载时完整移出视觉树。
上述控制和恢复回归通过，复测普通主窗口 CPU 0.64%，隐藏后 0.20%。

但本轮复测私有工作集仍为 167.6 MiB，隐藏后 170.5 MiB，**没有达到连续浏览后约 100 MiB 的目标**。
因此前文 106.6 MiB 的静止播放数据不能被当作全天候内存上限。
诊断用 `dotnet-gcdump` 会诱发收集，其输出只用于对象分析，不参与性能结果；
该诊断的托管存活堆约 9 MiB，不能把剩余 native/XAML/图形缓存都称为托管内存泄漏。
后续若要求所有浏览场景都稳定接近 100 MiB，还需要进一步针对原生资源缓存测量，
本轮不通过工作集清空或定时强制 GC 宣布达标。

## 连续切歌与回收验证（2026-10-07）

用户再次报告连续点击歌曲后超过 200 MiB。本轮直接读取当时运行的正式 Release 进程，
私有工作集约 252 MiB，总工作集约 439 MiB，而 `dotnet-counters` 托管堆约 7.7 MB，
GC 已提交约 22 MB。GC 计数有正常推进，因此不能把两百多 MiB 全部归因于托管堆。

本轮修正：

- 封面加载统一走受限尺寸的 `SetSourceAsync`，复用已有磁盘层下载；
  `ImageFailed` 仅在解码期间注册，完成或失败后退订，避免每张旧图长期绑定原生回调。
  同时限制并发解码为两张，缓存仍为 8 MiB/48 项。
- 切歌封面动画结束或被后一次点击取代时，主动停止动画、清空动画图片 `Source` 和 `Child`，
  摘掉几何裁剪；不只从画布移走控件。
- 磁盘缓存的进行中请求用 `Lazy<Task>` 去重，修复并发工厂重复启动、同步失败早于入表的竞态。
  增加同步失败后重试、并发读者仅下载一次的用例。
- 后台 Win2D 设备的中间表面缓存限为 8 MiB，低分辨率背景设备限为 2 MiB。
  这是缓存预算，不是进程/显存的硬上限；单帧所需资源可能超过它。
  歌词页在导航离场时主动释放视觉资源，不把释放完全交给随后何时发生的 Unloaded。

独立前后版本保存在 `artifacts/song-switch-performance/`，使用不同单实例互斥名称、
静音播放、独立 SMTC 应用标识，避免干扰用户的播放器会话和快捷方式。
同一批可见歌曲重复点播后，再进入歌词页按上一首/下一首循环切换，每轮都检查真实加载日志。
没有写入真实音源 URL 或凭据，没有用强制 GC/清空工作集作为结果。

## 发现、乐库与新歌单浏览验证（2026-10-07）

用户报告反复切 Tab、打开新歌单后约 256–300 MB，且没有播放 MV。
直接读取当时正式进程：私有工作集约 259 MiB，托管堆约 19 MB、GC 提交约 29 MB。
因此本次目标是实际浏览路径的资源收敛，不能用固定歌曲集合切换测试替代，
也不能把全部工作集解释成 C# GC 堆。

### 官方资料与适用范围

- Microsoft Learn 的《Optimize animations, media, and images for WinUI apps》说明：
  URI 图片内部缓存没有公开的 TTL、最大容量、淘汰顺序或清空接口；
  控件移出视觉树、放弃 BitmapImage 引用后资源可以被释放，但内存归还时间不保证。
  文档同时提醒，不同流的 SetSourceAsync 没有共享 URI 身份，会独立解码。
  本项目因此必须自行复用有界缓存中的位图，不能把换成流加载本身当作内存优化成功。
  资料：https://learn.microsoft.com/en-us/windows/apps/develop/performance/optimize-animations-and-media
- microsoft/microsoft-ui-xaml #9044（2023-07-17）报告 WinUI Gallery 反复导航时内存增加，
  当前为 Closed as not planned。它能说明社区确实报告过同类现象，
  但报告没有证明本项目使用的 Windows App SDK 2.5.1 出现同一个根因。
  资料：https://github.com/microsoft/microsoft-ui-xaml/issues/9044

没有在本次提交中升级框架，也没有通过定时强制 GC 或清空工作集制造下降。

### 浏览路径复现

独立 Release 测试不播放音频、不打开 MV，重复执行：
发现卡片进入歌单/AI 歌单、返回，乐库大类进入专辑详情、返回，
每轮进入三张不同侧栏歌单，再切排行榜、收藏、最近播放与我喜欢的。
每轮按实际能取得的内容执行，服务端返回速度会影响可点击专辑数。
原始结果同时保存阶段内存、线程、句柄和详情入口计数，避免只记录最低数字。

旧资源加载路径：初始 107.3 MiB，三轮结束分别 169.3、189.0、220.5 MiB，
等待 10 秒后仍 220.5 MiB，隐藏 5 秒后 219.4 MiB。
这已复现“只浏览就增长且不回落”，不能归因于 MV 解码。

本轮追加修改：

- 未知 CDN 返回的 3000×3000、4000×4000 等图片先经 BitmapDecoder 生成真实的小尺寸 PNG，
  WinUI 只接收缩略图流；SoftwareBitmap、输入流和编码输出流都在异步处理完成后释放。
  仅设置 DecodePixelWidth 不能作为编码数据与全部原生缓存都受限的证据。
- 普通页面卸载时解除无选择列表的 ItemsSource，释放已实现的模板、行菜单和图片呈现引用。
  数据由原 ViewModel 持有，回到缓存页面时重新关联并恢复滚动位置。
  页内带选择状态的 Tab 列表和歌词/MV 页面不走这一通用释放路径。
- 歌曲行的“更多”菜单改成打开时创建、关闭或卸载时释放，避免每条新行预建隐藏列表、按钮和状态。
- 每种详情页最多复用一个已经离开当前/返回栈、且已卸载的页面。
  换歌单时停止旧绑定、替换 ViewModel、刷新绑定，并重置旧图片/滚动与共享封面交接记录。
  仍在返回栈的页面不重绑定，保留原有返回语义。

等待后 211.1 MiB，**没有解决主要增长**；追加离屏列表释放后，四轮结束约 206.7 MiB；
