# 应用性能优化与验证（2026-10-02）

本轮目标是 120 fps（每帧约 8.33 ms），覆盖窗口操作、歌词、频谱、倒影、导航、封面和播放通知。
下面严格区分后台绘制频率、UI 输入响应和屏幕呈现；定时器频率不当作呈现帧率。

## 环境与测量

- Windows 10 22H2，系统版本 19045。
- AMD Ryzen 5 4600H，6 核 / 12 线程；NVIDIA GeForce GTX 1650 Ti。
- 主显示器 2560×1440，驱动报告 200 Hz；窗口处于 125% DPI。
- 使用本机 Release 构建，真实播放「花の塔」的 101 行逐字歌词。
- 重页面使用真实排行榜（20 个榜、124 个分组/榜头/预览条目）及实际搜索模板的一万条本地数据，避免仅测少元素页面。
- 通过 `BODIAN_LYRICS_DIAGNOSTICS=1` 记录绘制耗时、帧间隔、页面和窗口处理时间。
- 拖动/缩放使用物理像素鼠标输入，显式设置测试线程的 DPI 上下文；校验窗口位置/尺寸确实改变。
  随后用 `WM_NULL` 与 `SendMessageTimeout` 测消息响应，并检查页面未被切走。
- 全屏每轮核对窗口确实变成显示器尺寸并恢复原窗口；切换由另一线程触发 UI Automation，同时采样消息响应。
- `MoveWindow(..., repaint: true)` 和 UI Automation 调用本身含同步重绘/自动化等待，其总耗时不等同鼠标输入响应。
- PresentMon 能捕获当前会话的桌面合成及其他交换链，本程序的 CompositionDrawingSurface 没有独立可归属的交换链数据；不能据此宣布整应用实际呈现锁定 120 fps。

## 已确认的原因

### 窗口移动与缩放

采样栈落在 `Microsoft.UI.Input!InputNonClientPointerSourceWinRT::SetRegionRects_Callback`，随后通过
`CalculateUnionRectAndSetWindowPos_Callback` 移动输入辅助窗口。原实现每个窗口位置变化都经过这条路径。
同时歌词在 UI 的 `CompositionTarget.Rendering` 里绘制；宽度或字号变化又使整首歌词排版失效。

`WindowRenderActivity` 在交互或全屏切换期间合并位置变化的输入区域同步，标准窗口过程继续处理
客户区尺寸/位置，在松手或切换结束后把最终状态交给窗口层。最小化、显示/隐藏和销毁保持正常处理。
标题栏停止在每次全局布局更新时递归扫描；交互控件实际变化时主动重算区域。

### 最小化闪退

转储显示窗口层在调用 `AppWindow.Changed` 事件处理器后收到 `E_INVALIDARG`，进入原生 FailFast；
它不会按普通托管未处理异常的形式落日志。最小化也会带来 presenter 变化，旧歌词页回调把它当成
全屏切换，重设标题栏布局与按钮。现在先排除最小化，比较实际全屏状态，并在 COM 事件边界内记异常。

频谱采集器的 `Dispose` 还会等待 WASAPI 采集线程，旧代码在可见性事件里同步释放，也会卡住 UI。
启停现在由一个后台循环根据最新期望状态串行处理；频谱结果以不可变快照发布，UI 不再等待 FFT 或采集锁。

## 最终实现

- 歌词、频谱、倒影使用独立 Composition 表面与后台绘制线程，各自目标 120 Hz；XAML 属性由 UI 发布成输入快照。
- 使用高精度可等待计时器和绝对时间帧调度；长帧后跳过过时帧，不忙等、不全局修改系统计时器分辨率。
- 隐藏、最小化和全屏过渡暂停视觉刷新；普通移动/缩放继续动画，播放引擎、队列和 SMTC 继续运行。
- 整个窗口由 `ResponsiveViewport` 承载。120 Hz 帧预算内的轻布局可以实时提交；
  超预算的页面在连续缩放期间保留布局，逐帧只改合成变换，松手后一次提交准确排列与字号。
  这会暂时缩放现有文字/卡片，避免拖动边框时整树反复重排；不是把画面停在旧尺寸。
- 绘图线程结束后，Composition 对象回到创建它们的 UI 线程释放；设备丢失按同样边界重建。
- 首轮歌词只排整行与测量高度；实际播放到某行时才准备逐字区域和长音资源。缓存最多三份不同尺寸/字号的排版。
- 全屏使用同一个窗口的无边框显示器覆盖，保存 Win32 placement 与样式；退出恢复尺寸、位置及原最大化状态。
  原生样式/位置提交的等待在后台完成，重复全屏点击串行处理；不从绘图线程调用 XAML。
- 模糊封面背景使用固定分辨率缓存，由合成器缩放；隐藏被歌词页遮挡的外壳背景；相同原生按钮配色只提交一次。
- 通过共同的 `VirtualizedListView` 设置可回收面板、半屏预取，并限制无限高度/宽度到窗口视口。
  排行榜平铺到标题、榜头和曲目行；搜索综合页平铺不同结果类型；发现页平铺到每个卡片区。
  同一方向不再套外层 `ScrollViewer` 和内层列表。诊断直接读取实际实现容器，日志带进程 id。
- 搜索分页追加只初始化新增行的播放状态，避免每追加一项就扫描整批结果造成平方级开销。
- 常用根页按类型保留最多八个实例，重复导航优先复用；登录/登出重置时清缓存。
- 封面图片缓存最多 128 个条目、估算解码内存预算 64 MiB，列表解码宽度 256 px、主封面 1024 px；先设解码尺寸再请求图片。
  取色使用 60 px JPEG，并在后台读取像素和计算颜色，过期请求会取消和释放。
- 播放进度只保留最新值、最多排一个低优先级 UI 回调，避免窗口繁忙后重放积压通知。
- 发现页返回时重新挂滚动加载监听；卸载时继续解绑。

## 回归范围与限制

Core 回归增加通知合并、布局预算以及页面布局结构的用例，共 604 项通过。
结构回归覆盖排行榜/搜索/发现页不能重新引入外层滚动与整组 `ItemsControl`，
并检查所有页面的垂直列表不能直接放在无界 `StackPanel` 中。
测试不会证明未来任意模板都能锁定 120 fps，但会拦住本轮已确认的虚拟化失效路径。
窗口回归覆盖连续鼠标拖动/缩放、普通窗口/显示器全屏切换、最小化恢复、隐藏期间播放位置推进、
常用侧栏页重复切换和搜索输入。Debug 与 Release 的构建产物都应使用最新补丁。

120 Hz 是动态绘制目标。首帧、换歌、尺寸改变、驱动调度及首次图片资源仍可能出现长帧；
短样本的峰值或稳态不能证明所有页面、每次冷启动和多显示器组合都锁定 120 fps。
静态页面不需要不断重绘；滚动和系统合成以实际显示刷新率运行。

复测脚本与临时结果保存在 `artifacts/window-performance/`（不入版本控制）。
性能诊断默认关闭，只在启动前临时设置环境变量；日志没有添加音源地址或会话凭据。

## 后续页面重设计的性能约束

1. 页面放在既有 `WindowViewport` 下，保留有限视口尺寸，不绕过共同的缩放入口。
2. 单向滚动使用 `VirtualizedListView`；分组标题、行、卡片区作为数据项，模板选择负责显示。
3. 横向卡片使用可回收横向 `ItemsStackPanel`；避免一个虚拟化单位包含任意大的整组子树。
4. 图片走共同缓存，动画走 Composition 或后台绘图，UI 回调只发布输入和显示状态。
5. 重设计必须跑真实页面及大数据场景，比较已创建容器、输入延迟、首帧和稳态帧间隔。

可重复的大数据场景默认关闭，只在本机明确设置以下变量时使用真实搜索页模板：

```powershell
$env:BODIAN_LYRICS_DIAGNOSTICS = '1'
$env:BODIAN_UI_PERF_SCENARIO = 'search-list'
$env:BODIAN_UI_PERF_ITEMS = '10000'
& './src/Bodian.WinUI/bin/Release/net10.0-windows10.0.26100.0/win-x64/Bodian.WinUI.exe'
```

它不请求搜索接口，不写搜索历史，使用负数 id 的本地样本；正常启动没有样本数据。
测试结束后关闭该测试进程，使用未设置这些变量的终端正常运行应用。
