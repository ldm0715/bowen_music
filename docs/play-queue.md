## 1. 队列的内部结构：排列 + 游标

`src/Bodian.WinUI/Playback/PlayQueue.cs` 从「单个 `_index`」改成三个字段：

```
_items    : List<Track>    队列本体，**顺序就是抽屉里给用户看到的顺序**
_order    : List<int>      _items 下标的一个排列
_cursor   : int            _order 中的位置，-1 表示空队列
_mode     : PlayMode
```

`Current => _items[_order[_cursor]]`。

**为什么不是「洗牌打乱 `_items`」**：那样抽屉里的顺序会跟着随机变，用户上一眼看到的第 5 首
下一眼跑到第 12 首去了。把「显示顺序」和「播放顺序」拆成两份数据，
随机模式就只是换一条 `_order`，`_items` 全程不动。

- 顺序播放与列表循环时 `_order` 是恒等排列。
- 列表随机时 `_order` 是洗过牌的排列，**且轮转到当前曲目开头** —— 切到随机模式的那一瞬间
  当前曲目不能跳走。
- 切回非随机模式时按当前曲目重建恒等排列，**当前曲目同样不动**，只是它在 `_items` 里的
  真实下标成了新游标。

> ★ **增删曲目必须同时重映射 `_order` 里的下标**，这是本类最容易错的地方：
> 往 `_items` 的第 i 处插入，会让所有 `>= i` 的下标失效；删除则会让 `> i` 的整体前移。
> 出错不会立刻炸，只会让「下一首」跳到意料之外的地方。单测从**外部行为**上验这条不变量
> （顺序模式走一遍必须不重不漏地覆盖每一首），而不是去读那个私有字段。

队列的变更方法有六个，都触发 `Changed`（**只有一个例外，见下**）：

| 方法 | 语义 |
| --- | --- |
| `Replace(items, startIndex)` | 整页替换并落到第 N 首（**现在只由「播放全部」用**） |
| `Append(track)` | 加到队尾；**队列里已有同一首（按 Id）时不加，返回 `false` 且不抛 `Changed`** |
| `AppendRange(items)` | 批量追加，返回实际加进去几条；去重、跳过 `Id <= 0`、**整批只抛一次 `Changed`** |
| `InsertNext(track)` | 插到当前曲目之后 |
| `MoveToItem(itemIndex)` | 跳到第 N 首（抽屉点行用） |
| `RemoveItem(itemIndex)` | 删第 N 首 |

> ★ **`Append` 是唯一会「什么都不做」的变更方法。** 它返回 `bool` 就是为了让调用方
> 知道这次到底加没加进去 —— 行菜单的「加入播放队列」据此把提示从「已加入播放队列」
> 换成「这首歌已经在播放队列里」，而不是骗人说加成功了。

`Append` / `AppendRange` / `InsertNext` 都在**空队列上做了兜底**：把这一首放上去并落游标。
`MoveToItem` / `RemoveItem` 越界时返回 `false`。

**为什么 `AppendRange` 不能逐条走 `Append`**：队列面板是整表重建的，每抛一次 `Changed` 就重建一次，
几百首的列表会卡住。整批合并成一次事件是它存在的全部理由。

## 2. 三种播放模式

`src/Bodian.Core/Models/PlayMode.cs`。只有三个成员，**没有单曲循环**。

| 模式 | `MoveNext` 到头 | `MovePrevious` 到头 | `QueueExhausted` |
| --- | --- | --- | --- |
| `Sequential` 顺序播放 | 返回 `false`，**停止** | 返回 `false` | 会触发（播放条提示「已经是最后一首了」） |
| `ListLoop` 列表循环 | 环绕回第一首 | 环绕回最后一首 | 永不触发 |
| `Shuffle` 列表随机 | 一轮走完**重新洗牌继续** | 返回 `false`（不往回绕） | 永不触发 |

`Sequential` 保持改动前的行为。后两者属于「列表」家族，都不会自然结束。

**随机模式一轮走完要重洗，且避开刚放完的那一首** —— 否则一轮的末尾与新一轮的开头接上，
同一首连放两遍。`Reshuffle` 里有一条显式的兜底：洗完若首位仍是刚放完那首，就与随机一个位置对调。

> ★ **模式判断收在 `PlayQueue.HasNext` / `HasPrevious` 里，不要在调用方各写一遍。**
> `SmtcManager` 与播放条都直接读这两个属性，收在这里，系统媒体控件（键盘多媒体键、
> 音量浮层里的上一首/下一首）就自动跟着模式变灰或变亮，一行都不用改。

## 3. 协调器上的命令

`src/Bodian.WinUI/Playback/PlaybackCoordinator.cs` 新增：

| 方法 | 说明 |
| --- | --- |
| `SetPlayMode` / `CyclePlayMode` | 设模式并**落盘**；按钮按 `顺序 → 循环 → 随机 → 顺序` 轮换 |
| `EnqueueAndPlayAsync(track)` | **点行的入口**：插到正在播那首的后面并立即播它；队里已有则不重复加，跳到原来那一份 |
| `PlayFromAsync(list, index)` | 整表替换并从第 N 首播。**现在只剩「播放全部」两个调用点** |
| `AddToQueueAsync(track)` | 加队尾，返回是否真的加进去了 |
| `AddToQueueAsync(tracks)` | 批量加队尾，返回实际追加数 |
| `PlayNextAsync(track)` | 插到当前之后 |
| `PlayQueueItemAsync(itemIndex)` | 跳到第 N 首 |
| `RemoveQueueItemAsync(itemIndex)` | 删第 N 首 |
| `ClearQueue()` | 清空 |

三条行为上的决定：

1. **队列原本为空时，加队的几条命令直接开播。** 否则加了没有任何反应，用户会以为没生效 ——
   而「队列是空的」恰恰是第一次用这些入口时最常见的状态。
   批量版的判断是「追加数 > 0 且原本为空」：一首都没加进去（全是重复）时不开播，
   空队列没什么可播的。
2. **删掉的正好是当前曲目时才换歌**，其余情况不碰引擎。界面上正在播放那一行的删除按钮是置灰的，
   正常走不到这个分支；留着是因为队列是共享状态。
3. **清空不打断播放。** 正在放的那一首自然放完 ——「清空列表」说的是列表，不是「停止播放」。

自动续播（引擎报「放完了」→ `AdvanceAfterEndAsync` → `NextAsync`）**一行没改**，
模式判断已经收在 `PlayQueue` 里。

### 6.2 右侧抽屉

面板**不在播放条里**，而是挂在主窗口第 1 行（内容区）的覆盖层上 ——
抽屉要盖住内容区，而播放条自己就占着窗口最下面那一行，在这一层放不下。
所以 `PlayerBar` 只抛一个 `PlaylistRequested` 事件，开合归 `MainWindow` 管。

抽屉只覆盖内容区：**标题栏与播放条都露在外面**，拉着队列时还能搜索、还能暂停切歌。
收起方式四个：点空白处、`Esc`、右上角 ×、再点一次「播放列表」按钮。

控件与模型：

| 文件 | 职责 |
| --- | --- |
| `Controls/PlayQueuePanel.xaml(.cs)` | 面板本体：头部（标题 / 计数 / 清空 / 收起）+ 列表。**2026-10-05 起还管拖动排序的手势**，见 §12 |
| `ViewModels/PlayQueueViewModel.cs` | 整表重建、三个动作（切歌 / 删单曲 / 清空）、`IsOpen` |
| `ViewModels/PlayQueueRow.cs` | 一行：序号 / 封面 / 标题 / 歌手 / 时长 / 可否删除 / 可否拖动 |

三处讲究：

1. **整表重建，不做增量同步。** 队列变动不频繁，而增量同步要自己维护一套「哪一行对应哪个下标」
   的影子状态 —— 队列那边刚因为下标重映射踩过一遍，这里没必要再来一次。
2. **抽屉开着的时候才重建。** 队列每次切歌都会触发 `Changed`，而重建会清空再填满
   `ObservableCollection`、让 `ListView` 整个重新测量。抽屉没拉开就没人看，这份力气白花。
3. **重建排到 dispatcher 的下一轮。** 队列很可能就是在面板自己的事件处理里被改的
   （点行切歌、点行尾的删除），同步重建等于在 `ItemsControl` 处理事件的过程中把它脚下的集合抽掉。

**正在播放那一行的删除按钮置灰**：删掉当前曲目之后「要不要自动切下一首」没有不别扭的答案；
想跳过它就点下一首。界面这样定，`PlayQueue.RemoveItem` 就永远不会删到游标位置。

**清空要弹确认框**，默认落在「取消」上 —— 与项目里取消收藏、清空播放记录同一套写法。

未取字体文件、未取图标资源包，与本项目 GPL-3.0 相容。

> ★ **路径数据必须规范化后才能喂给 WinUI。** Fluent 的 SVG 用 `a.75.75` 这种
> **隐式分隔**（两个数字之间没有分隔符，靠第二个小数点断句），SVG 允许，但 WinUI 的

## 10. 2026-10-05：播到末尾再点播放

### 10.1 症状与根因

顺序播放放完列表最后一首后，引擎状态是 `Stopped`（`LibMpvPlaybackService.OnEndFile`），
而 mpv 因为 `keep-open=no` + `idle=yes` 已经把文件卸载了 —— **引擎里没有任何东西可播**。此时：

| 操作 | 现象 | 真正发生的事 |
| --- | --- | --- |
| 点播放键 | 没声音，但**歌词照滚** | `pause=false` 在 idle 的 mpv 上是**空操作**；`SetPause` 的乐观更新却把状态置成 `Playing`，歌词时钟据此开始按墙钟外推，而 idle 下读不到 `time-pos`、**根本不发进度事件**，没人能把它拉回来 |
| 拖进度条 | 弹「跳转失败：property unavailable」 | `time-pos` 在 idle 下不存在。更糟的是失败处理会把状态砸成 `Idle`，进度条跟着归零 —— 这才是「进度条异常」的来源 |
| 点某一行歌词 | 同上 | `LyricsViewModel.SeekToLineAsync` 走的是同一个 `time-pos` |

> ★ **`SmtcManager` 里本来就修对了一半**：系统媒体控件的播放键有 `Idle or Stopped => 重播当前这首`
> 这条分支，播放条那颗键漏了。两份判断分散在两处，正是这次漏一处的直接原因。

### 10.2 判断收在协调器的 `PlayAsync`

新增 `PlaybackCoordinator.PlayAsync`（`src/Bodian.WinUI/Playback/PlaybackCoordinator.cs`），
**所有播放键都走它**：引擎处于 `Idle` / `Stopped` 时不再直接调引擎的 `PlayAsync`，而是重新解析音源再 loadfile
（CDN 直链带签名且有时效，旧的很可能已经过期）。`PlayerViewModel.TogglePlayPauseAsync` 与
`SmtcManager` 那两处局部判断都并到这一个入口，与 §2「模式判断收在 `PlayQueue` 里」是同一条理由。

重新加载的目标分两种，靠协调器上的私有标记 `_queueExhausted` 区分：

| 状态 | 重播目标 |
| --- | --- |
| 队列已经播到头（顺序模式放完最后一首） | **整个队列从第一首重来** |
| 其余（试听片段结束、加载失败后重试） | 重播当前这首 |

`_queueExhausted` 在 `NextAsync` 的 `MoveNext()` 失败分支里置上，在 `PlayCurrentAsync` 里清掉 ——
**任何一次新的播放尝试都算翻篇**（六条队列命令全经由它），不需要每个调用点自己记得清。

配套给 `PlayQueue` 加了 `MoveToStart()`：把游标拨回**排列的第一位**（`_cursor = 0`，不是
`MoveToItem(0)`）—— 前者是「播放顺序的第一位」，不依赖面板里的显示下标；顺序模式下 `_order` 是恒等排列，
两者等价，随机模式下回到本轮洗牌的第一位。

### 10.3 停止态拖进度条：无效但不报错

`PlayerViewModel.SeekToAsync` 与 `LyricsViewModel.SeekToLineAsync` 都加了 `Idle` / `Stopped` 门禁。
被挡下时 `PlayerViewModel` 会补发一次 `PositionSeconds` 通知把滑块拨回原位 —— 滑块已经被拖走了，
而引擎在这个状态下不会再发进度把它拉回来。

> ★ 补发通知能拨回滑块是**验证过的**，不是想当然：x:Bind 生成的
> `Update_ViewModel_PositionSeconds` 是无条件 `RangeBase.Value = obj`，没有缓存比对
> （`obj/.../Controls/PlayerBar.g.cs`）。若哪天它改成带缓存的形式，这里会静默失效。

**不去动** `OnEngineStateChanged` 对 `Stopped` 不复位进度的行为：末尾停下时播放条上显示的还是那首，
进度停在终点是如实的。

### 10.4 已知边界

`ClearQueue()` 清空后当前曲目自然放完，`MoveNext` 在空队列上同样失败，于是也会被标记成「已播到头」。
此时点播放没有可重播的第一首，是静默无操作 —— 清空队列本身就不该保留可播内容，有意留着。

### 10.5 验证

**1184 项离线测试通过**（此前 1177，本轮新增 7）：

| 新增测试 | 覆盖 |
| --- | --- |
| `PlayQueueTests`（3 项） | `MoveToStart` 回到第一位、已在第一位时仍返回 `true` 并抛一次 `Changed`、空队列返回 `false` |
| `PlayQueueCommandTests`（4 项） | 耗尽后按播放从第一首重来；未耗尽而引擎停下时重播当前这首；`Paused` 时只恢复不重载；一次新的点播会清掉「已播到头」 |

`FakePlaybackEngine.RaiseEnded()` 改成**先置 `Stopped` 再触发 `Ended`**，对齐真引擎
（`LibMpvPlaybackService.OnEndFile` 也是先 `SetState(Stopped)` 再抛事件）—— 不这样，
「放完之后按播放」永远走不到 Idle/Stopped 那条分支，也就验不出真机上为什么没声音。

界面部分按惯例由用户手动验收：末尾停下后点播放是否从第一首重来、拖进度条是否只弹回不报错、
点歌词行是否不再弹红条、暂停态点播放是否仍只续播不重载。

## 11. 2026-10-05：点行的落点从队尾改成当前曲目之后

### 11.1 为什么

2026-10-04 把点行定成「追加到队尾并立即播它」（§1 的中括号、[`track-list-toolbar.md`](track-list-toolbar.md) §1）。
「不动队列原有内容」这一条是对的，但**落点挑错了**：

```
队列 [A, B, D]，正在播 A，用户点了 C

追加到队尾 → [A, B, D, C]，游标到 C
             C 一放完，后面什么都没有 → 顺序模式下直接 QueueExhausted
             「点了首歌，放完就断档」

插到当前之后 → [A, C, B, D]，游标到 C
             C 放完接着播 B → D
```

排到队尾等于**把正在播这首后面原本排着的歌整段跳过去**。用户点一首歌的意图是「现在听这首、
之后接着听」，不是「把队列撕成两半」。

> ★ 这个改动**不改**「队列原有的歌一首都不动」：`InsertNext` 只是把新曲目插进去，
> 其余曲目的相对顺序原封不动，只是整体后移一位。

### 11.2 实现

`PlaybackCoordinator.EnqueueAndPlayAsync` 换成两个既有原语的组合（`PlayQueue` 一行没改）：

```
IndexOfQueueItem(track.Id)              // Id > 0 时才比对，与 PlayQueue.Append 同一套规则
  ├─ 已有 → Queue.MoveToItem(那一份)     // 不重复添加
  └─ 没有 → Queue.InsertNext(track)      // 插到当前曲目之后
            Queue.MoveToItem(当前 + 1)   // 队列原本为空时 InsertNext 已落好游标，跳过
```

`MoveToItem` 取的是**显示下标**（`_items` 的），`InsertNext` 插进去的那一项恰好就在
「旧 CurrentIndex + 1」—— 插入点在当前曲目之后，所以当前曲目的下标不受影响，这个算式在
随机模式下同样成立（`_order` 里那一项由 `InsertNext` 直接落在 `_cursor + 1`）。

**已有同一首的那一支刻意不挪动它。** 挪了就是替用户重排队列；而「它已经在队列里」本身说明
它早就排好了，用户点它只是想现在听。代价是：如果那一份正好排在队尾，放完仍会碰到
`QueueExhausted` —— 这与点行无关，是那一份本身就在末尾。

### 11.3 与菜单两项的关系

| 入口 | 落点 | 立刻换歌？ | 去重 |
| --- | --- | --- | --- |
| 点行 | 当前曲目之后 | 是 | 去重，已有则跳过去 |
| 下一首播放（行尾菜单） | 当前曲目之后 | 否 | **不去重**，同一首可以排两份 |
| 加入播放队列（行尾菜单） | 队尾 | 否 | 去重 |

点行与「下一首播放」现在落点相同，区别收在「要不要立刻播」上：点行会换歌，菜单那条只排队。
这一轮的改动**没有**动两条菜单动作（`AddToQueueAsync` / `PlayNextAsync`）—— 曾考虑把
「加入播放队列」也改成插到当前之后，但那样两项就只剩去重一个差别、字面上分不开，所以维持队尾。

### 11.4 验证

**1185 项离线测试通过**（此前 1184）：`EnqueueAndPlay_InsertsRightAfterTheCurrentTrackAndPlaysIt`
（落点与下标）、`EnqueueAndPlay_LeavesTheRestOfTheQueuePlayable`（点完接着往下走、不触发 `QueueExhausted`）、
`EnqueueAndPlay_WhenAlreadyQueued_JumpsToItWithoutDuplicating`（补上「不挪动」的断言）。
另两条既有用例（空队列直接开播）未受影响。

界面部分手动验收：顺序模式下队列排几首、播到中间某首时去列表里点另一首，
① 队列抽屉里新点的那首应紧挨在正在播那首下面；② 它放完应接着播原本排在后面的那首，而不是停。

## 12. 2026-10-05：播放队列支持拖动排序

§9「本轮不做」里那条 `队列拖拽排序 | 未要求` 到此兑现。抽屉里鼠标悬停到某一行，序号位换成六点握把，
拖住它就能调整顺序。

### 12.1 三个取舍

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 范围 | **只加播放队列抽屉** | 歌曲列表的顺序来自服务器分页（歌单 / 搜索 / 专辑），拖动只能改当页显示，刷新或翻页就回去了。要真做得走服务端的歌单排序接口，是另一个量级 |
| 随机模式 | **不能拖** | 随机模式下面板顺序（`_items`）与播放顺序（`_order`）是两份数据。重排 `_items` 只会改变滚动条里的排列，听感完全一样，用户会以为拖坏了 |
| 正在播放那一行 | **不能拖** | 与「正在播那行的删除按钮置灰」同一套判断；且那一格的序号位已经被起伏条占着，再塞一个握把要抢位置 |

### 12.2 为什么不用 WinUI 内置的 `CanReorderItems`

内置那套会**直接改写绑定的 `ObservableCollection`**，而且是 Remove + Add 两次 `CollectionChanged`
（不是 `Move`）。但 `Rows` 只是 `PlayQueue._items` 的**快照**，权威数据在 `PlayQueue` 里 ——
让框架去改就是把两边掰开，还得再回写一次。手写还能顺带做到「只有握把能拖」（内置的是拖整行）。
项目里其它拖拽（进度条、音量、歌词滚动、图片平移）本来就全是手写 `CapturePointer`，风格也统一。

### 12.3 `PlayQueue.MoveItem(from, to)`

语义是 `List.Move`：**`to` 是挪完之后的最终显示下标**，不是插入槽位。拖放的「插到第 N 行之前」
由界面换算（`slot > from ? slot - 1 : slot`）。

```
if (!CanReorder) return false;        // 随机模式
越界 / from == to → return false，不抛 Changed
current = CurrentIndex
_items.RemoveAt(from); _items.Insert(to, track)
_cursor = Remap(current, from, to)
ResetToIdentityOrder()
Changed
```

> ★ **非随机模式下 `_order` 必是恒等排列**，所以 `CurrentIndex == _cursor`。
> 这条不变量来自 `ApplyOrderForStart`（非随机分支就是 `ResetToIdentityOrder`），
> 而 `Append` / `AppendRange` / `InsertNext` / `RemoveItem` / `MoveNext` / `MovePrevious` / `MoveToStart`
> 在恒等的前提下都保持恒等。于是「把 `_cursor` 挪到当前曲目的新下标 + `_order` 重建成恒等」
> 就同时给出**当前曲目不变**与**播放顺序跟着新的面板顺序走**。

> ★★ **不要改成「保住旧播放序列」的那种值重映射**（把 `_order` 里等于 `from` 的值改写成 `to`、
> 区间内的整体 ∓1）。那样 `MoveNext` 走出来的顺序与拖动前**完全一致** —— 而顺序播放模式下
> 面板顺序**就是**播放顺序，用户拖完听不出任何变化，只会以为功能坏了。
> 测试 `MoveItem_PreservesPlaybackOrderAsDisplayOrder` 就是钉这一条的。

**`CanReorder` 的判断必须收在类里**，不能只靠调用方：结尾那句 `ResetToIdentityOrder()` 在随机模式下会
**静默把洗牌序抹成顺序序**（模式仍显示「随机」，下一首却开始按面板顺序走）—— 极难查的损坏。
公开属性同时给界面控显隐，一个来源不漂移。这与类头「模式判断收在 `HasNext` / `HasPrevious`」同一条理由。

### 12.4 界面：握把 + 手写拖拽

序号位变成**三态互斥**（一律 `Center`）：正在播放 → 起伏条；悬停且能拖 → 握把；其余 → 序号。
悬停态照抄 `TrackListView` —— 行根 `Grid` 加 `Background="Transparent"` 与 `PointerEntered/Exited`，
事件里把 `PlayQueueRow.IsPointerOver` 置位（状态存在**行数据对象**上，容器回收时 `x:Bind` 自然重读）。

拖起来的**不是被拖那一行本身，而是另画的一张卡片**（`DragGhost`）：

| 角色 | 表现 |
| --- | --- |
| 被拖那一行 | 原地**隐掉**（容器 `Opacity = 0`，连它的悬停底色一起消失） |
| 其余行 | 按落点**整行整行地让位**（上移或下移一格，140 ms 补间），空出来的那一格就是落点 —— 不需要额外的插入指示线 |
| 卡片 | 跟着指针走的一张浮起卡片：不透明底 + 描边 + `ThemeShadow`，列结构与行模板逐列对齐，所以拎起来的那一瞬间与原行严丝合缝 |

> ★ **为什么不是「把那一行原地抬起来」。** 那需要在 `ItemsStackPanel` 里把某个 `ListViewItem` 提到最上层，
> 而它认不认 `Canvas.ZIndex` 找不到可靠依据。卡片画在 ListView **之后**（同级、后声明即在上层），
> 不依赖任何面板行为。

| 细节 | 做法 | 为什么 |
| --- | --- | --- |
| 让位的位移量 | 抽 `from` 插 `to` 之后原来的第 i 行落到 `Remap(i, from, to)`，只可能是原地 / ±1 格，所以按整行高度给 | 与 `PlayQueue.Remap` 同一套账。算出来是 0 的行也**显式摆回 0**，于是落点挪回去时它们会自己滑回原位 |
| 让位的补间 | `UIElement.TranslationTransition` + `Translation`，不用手写合成动画 | 一行一个属性赋值就够，`ResetVisuals` 也只是一次赋值。项目被 `StartAnimation(name, null)` 坑过一次（见 `PlayingBars`），这条路根本不碰那套 API |
| 握把的命中区 | 外面垫一层**撑满整格的透明 `Border`**，`PointerPressed` 挂在它上面 | 六点握把的墨迹只有六个半径 1.5 单位的小圆，点与点之间是空的；`Icon` 是没有背景的 `UserControl`，空白处不参与命中测试。挂在 `Icon` 上会变成「必须精准点在点上」 |
| 指针捕获 | 捕获在 **ListView** 上，不在握把上 | 握把住在会被回收的 `ListViewItem` 里，拖拽途中 `Rows` 一旦重建，捕获在握把上会随元素复用而语义漂移 |
| 移动事件 | `AddHandler(..., handledEventsToo: true)` | 兜底被容器标成 Handled 的那些 |
| 插入槽位 | 先用 `ItemsStackPanel.FirstVisibleIndex/LastVisibleIndex` 收窄区间，再在区间内问 `ContainerFromIndex` | 虚拟化下未实现的行返回 `null`；已实现的行连续，所以指针在可视区内必有边界行把它夹住 |
| 卡片跟手 | 记下起手时指针在行内的高度，卡片按同一个偏移跟 —— 不会跳到指针正中 | 抓哪儿是哪儿 |
| 松手不切歌 | 握把的 `PointerPressed` 里 `e.Handled = true` | 否则 `ListViewItem` 会把它当成一次行点击 |
| 拖到一半队列被改 | 订阅 `Rows.CollectionChanged` → 收掉手势 | `Refresh()` 走的是 `Clear()`；拖拽时正好一首歌放完自动续播就会走到这里，不收掉的话手里那个 `_dragFrom` 已经是旧行号 |
| 复位要扫全部已实例化的行 | `ResetVisuals` 无差别把 `Translation` 与 `Opacity` 摆回默认 | 容器会被回收，一个带着平移或透明度的容器去装另一行时会把那副样子一起带过去 |
| 抖动 | 位移不足 4 DIP 不算开始拖 | 同 `LyricsCanvasView` 的阈值 |

**已知边界**：握把只在鼠标悬停时出现与生效，**触屏不参与拖动** —— 手指按下去不会先悬停，
要从触屏拖得另做长按手势。这是有意的。

## 13. 2026-10-07：队列持久化与续播

### 13.1 做了什么

退出后重进，队列还是上次那批歌、上次听的那首仍高亮，点播放**从上次停的那一秒**继续
（不自动播放，不会突然出声）。设置页「播放」分类多一个「记住播放列表」开关，**默认开**。

落到 `%LOCALAPPDATA%\Bowen\accounts\<uid>\queue.json`（2026-10-08 起按账号分目录；
「记住播放列表」开关则挪进了 `playback.json`，见 `multi-account.md`），与 `playback.json` 分开 ——
那份几行、很少写；这份几百首、每次增删切歌都要重写。

### 13.2 存的是快照，不是曲目

条目是独立的 `QueuedTrack`，照抄 `PlayHistoryEntry` 的做法：曲目是对外展示模型，字段会随
界面需求变，一旦给它加一个 `required` 属性，磁盘上的旧队列就会整条反序列化失败、凭空消失。

**快照里只有 `Id` 是 `required`**，其余一律给默认值 —— 几百条的队列里，任何一个字段以后
被改名都不该让整条队列一条不剩。加载时按「没有 id 或没有标题」丢弃坏条目。

集合一律用数组不用 `IReadOnlyList`、时长存秒不存 `TimeSpan`：都是仓库既定方针。

### 13.3 源生成反序列化不保留初始化器

**踩到的真坑。** 快照上写着「条目数组默认空」「开关默认开」，但 JSON 里缺这两个键时，
读回来的是 `null` 和 `false` —— 源生成反序列化对缺失的键一律留类型的零值，
属性上写的初始化器不生效。

后果不是「设置丢了」而是**应用起不来**：协调器构造时取条目数组的长度抛空引用。
所以读取路径里有一层补齐：顶层数组缺失就整份退回默认（文件损坏或被人手工改过），
条目里的数组同样补齐 —— 那是以后给条目加字段时旧文件会走到的路。

（音量那份是**位置 record**，默认参数在缺键时生效，所以不需要这层；这一点也钉进了它的测试。）

### 13.4 恢复时机：构造函数里，先恢复后订阅

在协调器构造函数里，读完播放模式之后、挂落盘钩子之前恢复。

**顺序不能改。** 那一刻一个订阅者都没有（播放条、队列面板、系统媒体控件都依赖协调器、
构造都在它之后），所以填充队列抛出的变更事件引发不了任何反应 ——「刚读出来就写回去」与
「往系统媒体面板注册一条假会话」这两条在结构上不可能发生，因此不需要一个「加载中」的守卫标志。

**但代价要补。** 订阅者错过了那一次变更，就不会做初始化：播放条的上一首/下一首按钮取自
队列的可用性、只在队列变更事件里刷新 —— 不补一次就是灰的。恢复路径显式刷一遍。

### 13.5 播放条要铺，但只铺播放条

恢复出来的那首必须铺到播放条上（复用「播不成」那条既有状态）：不铺的话没有曲目，
**播放键是禁用的**，用户根本没有入口把它放起来，也就无从「点播放继续」。

**刻意不喂系统媒体控件、不喂歌词页。** 前者不该为「没在播的歌」注册会话；
后者会为它发一次取词请求。恢复后队列面板那一行会显示静态的起伏条（引擎没在播，动画不动），
属已知行为。

### 13.6 续播走起播位置参数，不走跳转

位置交给引擎的起播参数（mpv 的 `start=`），**不是**加载完再 seek：文件还没打开时
位置属性不存在，设它会抛错、把引擎状态砸成闲置并弹一条错误条。换音档位续播用的也是
这条机制，仓库里已有先例。

**只给当前曲目记一个进度**，不给每首记 ——「切回队列里某首旧歌、听到上次没听完的前奏」
比不记更烦人。配对用**曲目 id**：用户换了歌，id 对不上自然失效，不需要在切歌路径上清理。

**距末尾不足 10 秒就不续播**，从头来。用绝对秒数不用百分比：10 分钟的歌只剩 30 秒值得续，
3 分钟的歌只剩 9 秒不值得，百分比在两处都算错。

### 13.7 写盘时机

队列变更 + **1 秒防抖** + 播放进度每 30 秒一个检查点 + 暂停/播完补一次 + 退出前同步落盘。

**不只靠退出时保存。** 点 ✕ 是关到托盘，窗口关闭被取消、退出流程根本不跑 —— 而这个应用
绝大多数会话就停在托盘里。只写退出那一次等于多数时候都没存住。

快照在 UI 线程抓（队列是个列表，不能跨线程读），序列化与磁盘写下放后台线程。

**开关关掉时**，同一次原子写里把已存条目清空 —— 用户说的是「别记我的播放列表」，
留一份在盘上等下次打开复活与这句话相反。内存里的队列不动，正在播的那首照常。

### 13.8 已知限制

| 项 | 说明 |
| --- | --- |
| 随机模式下恢复会重新洗牌 | 当前曲目不变，但「原本的下一首」丢了 |
| 强杀丢最后约 30 秒 | 进度检查点的间隔 |
| 恢复出的队列里有下架的歌 | 点它才会失败并如实提示，不做恢复期预校验（直链带签名有时效，预取没有意义） |
| MV 音量不持久化 | 另一套 0–1 标度，见 [`settings.md`](settings.md) §3.8 |
| 队列面板当前行显示静态起伏条 | 引擎没在播，动画不动 |
