# 设置页

设置页是标题栏那颗齿轮进入的根页，页内分「外观 / 播放 / 歌词 / 快捷键 / 存储 / 关于」六类。
这一篇记录的是**为什么这么做**，不是界面长什么样。

2026-10-07 补充：主题切换使用 650 ms 的独立合成遮罩，保留完整的主题资源解析；分类内容也接入统一入场动画。实现约束、浅色样式回归的修复及验证见 [应用动画](animations.md)。

---

## 1. 入口与布局

### 1.1 为什么不用 `NavigationView` 自带的设置项

`MainWindow.xaml` 里 `IsSettingsVisible="False"` 是**必须保持**的，不能改成 `true`。

侧栏「创建的歌单」那一段的高度是**算出来的**（`MainWindow.SyncPlaylistSectionHeight`），
公式建立在「`NavigationView` 自己不做页脚高度分配」这个前提上，而那个前提成立的条件正是
没有 `FooterMenuItems`、且 `IsSettingsVisible == false`。打开它会让菜单区多出一项，
把歌单段顶掉。详见 `ui-refresh.md` §19.2。

所以入口是自建的：标题栏右侧、小窗按钮右边那颗齿轮。它走 `Navigate<SettingsPage>()`，
也就是**压栈**。

### 1.2 为什么是压栈而不是换根

「从发现进去，返回就回发现；从排行进去，返回就回排行」——这是压栈的语义。
换根（`NavigateRoot`）会把历史全丢掉，返回键随之失效。

附带效果是侧栏高亮留在原来那一项（`Root` 没变）。这与详情页一致：设置是从当前位置
临时打开的一层，不是侧栏上的一个位置。

### 1.3 页内分类栏

`ListView` + 左栏右内容，**分类切换是页内 `Visibility` 切换，不走导航栈**：

- `MainWindow.SyncSelection` 按 `_navigation.Root` 的**页面类型**反查侧栏高亮，
  用 `Navigate` 切分类会让返回键变成「回上一个分类」。
- 分类是视图状态，不是导航状态。

不用嵌套 `NavigationView`：那会把 pane 背景、亚克力与自适应逻辑一并带进来。
`ListView` 顺带免费给到上下键导航与选中态。

**选中底是画出来的，不是列表项自己画的**（2026-10-07）：分类栏就是「一条不能收起的侧栏」，
所以与侧栏共用 `Controls/SelectionPill` —— 选中项一变，那张浮动 `Border` 从旧位置滑到新位置。
代价是两件事必须一起做对：

- 列表项自己的选中底要在 `ListView.Resources` 里压成透明（`ListViewItemBackgroundSelected` 及其
  PointerOver / Pressed 三个键，写法同 `AudioQualityPicker.xaml`），否则会出现
  「旧项瞬间亮着 + 高亮块慢慢追上」的双高亮；
- 高亮块要画在列表**之下**：包一层 `Top` 对齐的 `Grid`，`Canvas` + `Border` 在前、`ListView` 在后。
  因此这条栏必须保持透明底（`Background="Transparent"`）—— 项的文字才压在高亮块之上。

底色用 `SelectionPillBrush`，与 `NavigationViewItemBackgroundSelected` 同色号
（`#1A000000` / `#1AFFFFFF`），高对比度那档是 `Transparent`（保留系统自带的选中底）。

**窄窗口下收成 40 DIP 图标轨，不折行、也不变成横向条**——那种横排页签正是这一页要避开的形态。
阈值 720 = 栏 200 + 间隔 24 + 内容下限 496，按页面自身宽度判。最小窗口（800）下必然是图标轨，
这是预期不是退化。

## 2. 三种值：实时状态、默认值、当前值

这是这一页最容易做错的地方，单独说清楚。

### 2.1 实时状态（改哪边都跟着变）

主题、播放模式、桌面歌词的整套外观，都是**同一个单例上的同一份值**。
设置页与别处的入口（标题栏主题按钮、播放条模式图标、歌词条自己的设置面板）绑的是同一个对象，
一处改另一处自动跟着变，不需要谁去同步谁。

设置页因此**订阅**了这几个单例的 `PropertyChanged`，在 `OnNavigatedFrom` 里退订 ——
与 `LyricsPage` / `SearchPage` 是同一套写法。不订阅的话，临时的页面 ViewModel 会被
单例的事件表一直按住。

### 2.2 默认值（只由设置页改写）

**译文默认开关、默认音质、列表显示**这三项是「默认值」。语义是：

> 设置页决定**下一次的行为**；在别处做的调整只影响当前这一次，不写回默认值，也不需要重启。

拆开之后各自长这样：

| 项 | 默认值（落盘，只由设置页写） | 当前值（不落盘） |
| --- | --- | --- |
| 译文 | `LyricsSettings.ShowTranslation` | `LyricsViewModel.ShowTranslation` |
| 音质 | `PlaybackCoordinator.PreferredQuality` | 当前曲目的音源档位 |
| 列表显示 | `ViewModeSettings.UseGrid` | `ViewModeService.UseGrid` |

几处要点：

- **切换音质不再改默认值。** 原先 `PlaybackCoordinator.SwitchQualityAsync` 在三处顺手调了
  `SetPreferredQuality`，也就是「播放条上切一次档位，下一首取源也跟着变」。三处都删了，
  现在只有设置页能写默认值。这条改动与旧行为相反，`PlaybackQualitySwitchTests` 里那条断言
  随之更新，注释里写明了是有意改的。
- **歌词页那颗译文按钮不再落盘。** `OnShowTranslationChanged` 只重排当前文档。
- **每次打开歌词页都从默认值起步。** 只在构造函数里读一次的话，应用启动那一刻的值会一直
  粘到进程结束，中途在设置页改了默认值，已经打开过的那次也不会重新按默认值来。
- **写默认值时当前也立刻跟上**，所以改完不必重启、也不必去各页面手动切一遍。

### 2.3 桌面歌词的开关是状态，不是默认值

`DesktopLyricsSettings.IsEnabled` 是一个**当前状态**：歌词条被打开时它为 true，
设置页的开关跟着亮；关掉窗口它变回 false。两处是同一个值的两个入口，不存在谁覆盖谁。

**但它要落盘**：上次退出时开着，下次启动就自动出现。默认关，首次使用不会平白多一个浮窗。

这里踩过一个坑：宿主 `DesktopLyricsWindowHost` 只对 `IsEnabled` 的**变化**作出反应，
而开关落盘之后，启动读到 `true` 却没有任何变更事件，窗口就永远建不出来 —— 表现为
「按钮是亮的，桌面上什么都没有」。修法是 `ApplyInitialState()`，在 `window.Activate()`
之后调一次（悬浮窗要拿主窗口当 owner，早于它会失败）。没有歌曲时窗口显示「波点音乐」，
有歌没歌词时显示「暂无歌词」，这一行本来就由 `DesktopLyricsCanvasView` 负责。

## 3. 快捷键

### 3.1 只做应用内

不注册全局热键（`RegisterHotKey` / `WM_HOTKEY`）。取舍是**应用失去焦点时不响应**——
这正是应用内快捷键该有的语义，也避免了与其它软件抢占组合键。界面上有一句话说明这一点，
否则用户会以为是坏了。

### 3.2 键位表

`ShortcutKey` 的枚举值**刻意等于 Win32 虚拟键码**，与 `Windows.System.VirtualKey` 是同一套码，
所以「按下哪个键」到「绑的哪个键」是一次 `checked` 转换，不需要维护映射表 ——
那种表最容易在加键时漏一项，而漏了的表现就是某个键绑不上。

`Escape` **不在枚举里**。它是 shell 与沉浸页共用的收起键，收进枚举就等于允许用户改掉，
那会同时废掉歌单浮层、播放队列抽屉与搜索面板三条关闭路径。

`ShortcutModifiers` 只有 Ctrl / Alt / Shift，**不含 Win 键**：Win 组合被系统大范围占用，
绑上去多半被系统先吃掉，表现为「设了没反应」。

### 3.3 哪些键允许裸绑

**只有空格与 F1–F12。** 其余键（字母、数字、标点）单独按下都会产生字符，绑上去等于把打字
废掉——用户在搜索框里敲一个 `L` 就切了歌。规则在 `ShortcutKeyRules` 里，录制对话框与文件
校验共用同一份，不会出现「录的时候放行、读回来又剔掉」。

`F11` 是允许裸绑的，而歌词页 / MV 页自己也用 F11 做全屏，所以沉浸态下它会落到页面那一边。
这是已知的不一致，不打算修（那两页的全屏更常用）。

### 3.4 三条抑制规则

`MainWindow.OnShortcutInvoked` 里，按顺序：

1. **输入类控件聚焦时一律不接管。** 不只是「别用空格切歌」——更要紧的是 `Ctrl+←/→`
   在文本框里是「按词移动光标」，接管了就把搜索框的正常编辑破坏了。
   判定覆盖 `AutoSuggestBox`，标题栏那颗搜索框就是它。
2. **沉浸态（歌词页 / MV 页）下的裸键交给页面自己**，那两页各有自己的空格与 F11。
   带修饰键的手势它们没占用，照常生效。显式判而不是赌框架的派发顺序。
3. **录制期间不参与**：见下。

加速器挂在 `ShellRoot` 上并加 `KeyboardAcceleratorPlacementMode="Hidden"`。
不设 `Hidden` 的话，WinUI 会把加速器提示塞进子树里所有自带提示的控件，
出现「悬停播放条却显示空格」——与歌词页那三颗加速器同一条理由。

改键走 `IShortcutService.Changed` → 重建加速器，立刻生效。

### 3.5 录制改键

`ContentDialog` 包 `ShortcutRecorderContent`。

**对话框天然解决了「录制时别把动作也触发了」**：它挂在窗口的 popup root 下，
不在 `ShellRoot` 这棵子树里，所以 shell 那批加速器解析不到它，不需要额外的「录制中」开关。

内容体用 `handledEventsToo: true` 注册 `KeyDown`：空格与 Tab 会被对话框的焦点导航先吃掉，
不带这一项就永远收不到它们，而空格恰恰是默认键位之一。焦点必须在录制区上
（`IsTabStop=True` + `Loaded` 里 `Focus`），否则按键全被对话框的按钮收走。

必须显式给 `XamlRoot` 与 `RequestedTheme`：代码构造的 ContentDialog 不在可视树里，
不给主题的话深色模式会弹一块白板。

校验就地提示、不关框：`Esc` 不可绑、「这个键要配合修饰键」、以及「已被「XX」占用」。
撞车时**拒绝**而不是自动顶掉别人 —— 顶掉哪一边是用户的选择，不是控件的。

### 3.6 音量快捷键要露出滑条

按 `Ctrl+↑/↓` 时 `PlayerViewModel.Volume` 变了，但滑块藏在弹层里 —— 不露出来的话用户只能盲调。

`VolumeButton` 订阅它那份 `IVolumeSource` 的 `PropertyChanged`，音量一变就把弹层露出来，
**停留 1.6 秒**（鼠标移开是 250 ms；一按键闪一下等于没显示），连按则从最后一次重新计时。
已经开着时什么都不做——用户正在拖滑条时音量也在变，重新定位会让弹层跟着手指跳。

**静音变化走同一条。** `IsMuted` 也在那个订阅里（2026-10-07 加），所以按 `Ctrl+M` 时弹层同样会露出来 ——
否则用户只看到图标变了、不知道这意味着音量被压成了 0。

播放条、歌词页、MV 页共用这一个控件，各自跟自己的音源。

### 3.7 静音开关（2026-10-07）

出厂 `Ctrl+M`，可在设置页改（行序在「音量 -」与「收藏歌曲」之间）。快捷键这里只调
`PlayerViewModel.ToggleMute()` —— 与点击音量图标是同一条，不另写一套。

**静音不是「把音量设成 0」。** 音量字段保持原值，只有送给播放引擎的那个数是 0。好处是滑条停在原值不动、
恢复时也不必先记住原来多少。规则收在 `Bodian.WinUI/Playback/VolumeState.cs`：一个标记 + 两条规则
（切换、显式改音量即解除），**不持有音量数值**，所以 0–100 的播放条那套与 0–1 的 MV 那套共用同一份。

**「改音量即解除静音」这条不能省。** 拖滑条、按 `Ctrl+↑/↓` 都算「用户要听见声音」；
少了它会出现「图标显示静音、音量却在往上走」的鬼状态。落点在两个视图模型的 `OnVolumeChanged`。

**音量快捷键还要多一步。** 静音时数值恰好在 100（或 0），按对应方向键算出来还是同一个数，
`OnVolumeChanged` 根本不会触发 —— 所以 `ShortcutService.AdjustVolume` 先解除静音再改数值。
只靠上面那条规则的话，用户会遇到「按了没反应，还是没声音」。

静音**不落盘**：它和音量数值是两回事 —— **音量自 2026-10-07 起会落盘**，静音不会。

**验收状态**：代码与离线测试已完成，界面观感待用户手动验收（见 [`backlog.md`](backlog.md)）。

### 3.8 音量持久化与「记住播放列表」（2026-10-07）

两项都是「退出重进之后接着上次」：音量存 `%LOCALAPPDATA%\Bodian\volume.json`，
播放队列存 `...\queue.json`。写法与其它偏好逐字一致（先写 `.tmp` 再 `File.Move` 覆盖、
读失败退默认且保留坏文件、写失败只记 warning）。

**音量只记数值，不记静音。** 静音落盘会造出「上次静音退出、这次启动没声音，用户以为应用坏了」，
多数播放器也不记。注意滑条拉到 0 退出时，恢复后显示的是静音图标 —— 那是「音量是 0」的
正确语义，不是记住了静音。

**音量只管音乐播放那一套（0–100），不管 MV。** MV 走系统媒体播放器、标度是 0–1，
且 MV 页的视图模型每次进页都是新实例，今天本来就不记；把它并进来是新增行为变化，不是持久化。

**音量写盘防抖 1 秒。** 拖滑条每像素都会触发一次改动，与窗口位置那套防抖同一个数量级。
这与其它偏好「改了就立刻落盘」不同 —— 那些是低频改动，音量不是。引擎侧不受防抖影响，
永远立刻生效。

**两份都单独成文件，不并进 `playback.json`。** 那个文件今天存的是**裸的播放模式字符串**，
把它升级成对象会让旧文件反序列化失败、静默重置用户一次播放模式。而且写入频率差三个数量级，
混在一起只会让读写互相牵制。

**装载时「读出来的值」不写回。** 用守卫挡住落盘，但**不挡送引擎** —— 赋播放条的音量就顺带
把值送进了引擎（这时引擎还没初始化原生库，只会记住字段，首次播放时再补写进去）。

队列那一侧的设计、恢复时机与已知限制见 [`play-queue.md`](play-queue.md) §13。

**验收状态**：2026-10-08 用户确认功能正常。

## 4. 封面磁盘缓存

### 4.1 位置与形态

`%LOCALAPPDATA%\Bodian\cache\covers\`，文件名是键、内容是**CDN 返回的原样字节（编码后）**，
不是解码后的像素。解码后的占用取决于图片尺寸，通常高于压缩字节；界面层「先设解码尺寸再请求图片」这条约定
（`performance.md`）正是靠原样字节保留的。

它是内存缓存 `CoverImageCache` 的**持久化后盾**。内存命中时复用已有位图，不重新发起加载；彻底加载失败的条目会移除，下次绑定时可以重新请求。

### 4.2 键必须含解码边长

键 = `SHA256(改写后的绝对 URL + "\n" + 解码边长)`，小写十六进制。

**漏掉边长就会出错**：同一张封面在列表里按 256 取、在播放条上按 1024 取，CDN 按尺寸段返回
不同字节。键里不带边长，就会把大图位置填上小图，表现为发糊。
键使用本次实际加载的地址（经 `CoverArtUrl` 处理），查询参数会保留并参与哈希。首选地址与备用地址各用自己的磁盘键；内存缓存则复用首选地址与解码边长对应的同一个位图。

### 4.3 `Get` 必须保持同步签名

`CoverImageCache.Get` 被 `Formats.CoverSource` 在 `x:Bind` 里同步调用，分布在十几个页面的
模板中。改成返回 `Task` 要动全应用所有模板，爆炸半径不可接受。

所以磁盘命中那条路走 `BitmapImage.SetSourceAsync` —— 它允许图片先挂到 `Image.Source`、
之后再填充，「先给控件、后有图」是安全的。**流必须在 `SetSourceAsync` 完成之后才释放**，
提前释放会得到一张空图。

本地文件读取或解码失败时，尝试移除该文件并重新从同一地址加载。磁盘读取期间的 `ImageFailed` 由读取任务处理；网络仍失败时，再按 §4.6 尝试备用地址，避免两条失败路径同时改写位图。

### 4.4 容量与淘汰

默认上限 **256 MiB**。淘汰只看**最后写入时间**，不做读访问记账：精确 LRU 要么每次读都写一次
文件、要么维护一份每次读都改写的索引，两种代价都不值；而「用户实际浏览过的封面」这个工作集
用写入顺序近似已经足够——刚看过的图刚写过。

写入用「先写 `.tmp` 再 `File.Move(overwrite: true)`」：读者永远看不到半截文件，
而半截文件 = 解码失败 = 退回网络，静默退化，很难查。

按 key 去重 in-flight 下载（虚拟化容器会在一次滚动里反复要同一张图），
并用 `SemaphoreSlim(4)` 限流——别把别人的 CDN 当压测对象。

**写穿是 fire-and-forget，所有异常自己吞**：它由界面层 fire-and-forget 调用，
漏出去会变成未观察任务异常，被记成 Critical 日志。

### 4.5 清理

`ICoverDiskCache.ClearAsync` 清空目录内的文件（含 `.tmp`）；界面层的
`CoverImageCache.Clear()` 丢内存那份，由 `StorageSettingsViewModel` 在清理后调用。

**正在显示的封面不会消失**：位图已经解码在内存里并挂在 `Image.Source` 上，
删掉文件只是下次要重新下。

封面取色缓存（`CoverPaletteLoader`）**不参与清理**：它每个 `AmbientBackdrop` 实例各一份，
键是 trackId 而不是 URL，全局清理够不着它。这不影响正确性，不要为了能清它把它改成 DI 单例。

### 4.6 图片地址与失败回退（2026-10-06）

列表与详情接口可能给同一歌单或歌手返回不同的 `pic`。进入详情后有图，只能说明详情地址可用；
图片能否加载要看实际 URL，不能仅凭歌单的 `source` 判断，也不能把所有 `_o.jpg` 都当成错误。

`CoverArtUrl.Jpeg` 只对 `.kuwo.cn` 下的 `/star/albumcover/<尺寸>/` 与
`/star/starheads/<尺寸>/` 改写尺寸，并把已知路径的 `.webp` 改为 `.jpg`。
列表按 256 px 请求这些 CDN 缩略图；其它路径保留原样。只设置 `DecodePixelWidth` 不会缩小网络下载的原图。

`CoverImageCache` 保持同步返回同一个位图，网络加载失败后最多尝试一次备用地址：

- `y.gtimg.cn/music/photo/album_<数字>/<数字>/<数字>_albumpic_<数字>_o.jpg`
  尝试数字 `0` 的 `_0.jpg`，并保留查询参数；只匹配这个图床和已知路径。
- 酷我尺寸或格式改写后的地址失败时，回退接口给的原地址。
- 没有备用地址或备用地址仍失败时，从内存缓存移除对应条目；下次绑定可重新请求。
  旧位图被淘汰或清空后，其迟到的失败事件不会移除同地址的新条目。

## 5. 存储

只有四类可清，**凭据、窗口位置、各种偏好都不在里面**——「清除缓存」不该把用户设过的东西
一起清掉。

| 项 | 清理语义 |
| --- | --- |
| 封面缓存 | 清空目录内文件 + 丢内存那份，见上 |
| 播放记录 | `IPlayHistoryStore.ClearAsync`。清完「最近播放」页自然空了（那页每次进入重读），**不需要 sink** |
| 搜索历史 | **必须走 `ISearchHistorySink`**，见下 |
| 日志 | 只删**非当天**的文件，逐文件 try/catch |

### 5.1 搜索历史为什么需要 sink

搜索面板的 ViewModel 是单例，构造时把历史读进一个内存集合并**只写不回读**。
设置页若只调 store 落盘，当前会话里建议列表仍然是满的，要重启才消失。

`ISearchHistorySink` 让设置页走的正是搜索面板那颗清空按钮的**同一个命令**，两处永远一致。
接线方式与 `INoticeSink` / `IQueueSink` 相同。

### 5.2 日志为什么删不掉当天那份

Serilog 正持有它的文件句柄。删了要么抛 `IOException`，要么更糟——让后续写入落进一个
已经不在目录里的文件。判据是文件最后写入日期。

单个文件删不掉时计入结果的 `Message`（显示成「有 N 个日志文件正被占用，未能删除」），
**不让整次清理变成失败**：能删的照样删掉。

### 5.3 腾出的量按清理之前算

播放记录清完文件还在（内容变成空数组），事后去量会得到 0，而用户刚刚明明看到那一栏有几百 KB。
所以 `ClearFileAsync` 先量再清。

### 5.4 测试用的根目录

`StorageMaintenanceService` 的 `rootDirectory` 参数默认取 `AppPaths.LocalAppData`，
**测试指向临时目录**——否则「清理播放记录」这类用例会把跑测试这台机器上的真实历史删掉。
文件名仍从 `AppPaths` 取，避免同一个名字在两处各写一遍。

## 6. 版本与检查更新

### 6.1 版本号的唯一来源

`src/Directory.Build.props` 里的 `<Version>0.1.0</Version>`。放在那里而不是某个 csproj：
一行同时覆盖 Core 与 WinUI，免得两个程序集各自写一个版本号、慢慢对不上。

`IncludeSourceRevisionInInformationalVersion` 必须关掉：SDK 默认会把版本号拼上
`+<git sha>` 的悬挂后缀，关于页上会显示成「0.1.0+3fa9c1」。

关于页读 `Assembly.GetName().Version`，**不用 `Package.Current`**——本项目 unpackaged
运行，没有 MSIX 身份，它会直接抛。

### 6.1.1 关于页的布局

居中一列：图标 / 应用名 / 版本号 / 非官方声明 / 一排按钮 / 版权行，**不写「关于」分组标题**
（整块已经很明显，顶上再挂一个只会把居中列压得偏下）。

- **图标目前是占位**（`IconNote` 加一个圆角底）。设计稿定下来之后换成图片资源，
  这一处是 `SettingsPage.xaml` 里那个 96×96 的 `Border`。
- 按钮圆角用 `RadiusMd`（8）的圆角矩形，**不用 `RadiusPill`** —— 拉满会变成橄榄球，
  与这一页其它圆角卡片不是一套语言。三个按钮共用 `BodianAboutButton` /
  `BodianAboutAccentButton` 两个样式，内边距必须一致，否则同一排会一高一矮。
- **按钮三个**：项目主页、GitHub 仓库、检查更新。前两个指向还没建的仓库，
  在 `AppUpdateOptions` 填上之前是**禁用**状态（有 ToolTip 说明「仓库公开后可用」），
  不是坏了。检查更新用强调色按钮（`BodianAboutAccentButton`），走品牌色。
- 参照物上那个「支持作者」按钮**刻意不做**：本项目不接受赞赏。
- 「打开日志目录」没有放在这里 —— 「存储」分区的「打开数据目录」已经覆盖同一个需求，
  两处各放一个只会让人不知道该点哪个。

### 6.2 检查更新只做了壳子

`AppUpdateOptions` 是**唯一配置点**：`Owner` / `Repository` / `ProjectUrl` 三个字段，
仓库建好后填上前两个，检查更新就通了，不需要改服务、也不需要改界面。

`IAppUpdateService.CheckAsync` **永不抛**，返回四态之一：`NotConfigured` / `UpToDate` /
`UpdateAvailable` / `Failed`，`Message` 永远是人话而不是异常串。
未配置时**立刻返回、一条请求都不发**（这条有单测盯着）。

不打包自动更新：unpackaged 没有 MSIX 身份，装不了 `PackageManager` 那套。
查到新版本只会打开浏览器。也**刻意不做自动检查**——不启动时静默联网、不后台轮询，
与本项目「不含遥测与日志上报」的立场一致。

### 6.3 ⚠️ 不要把 `service/version/check/pc` 当更新源

那个端点返回的是**官方客户端**的协议版本（`{"version":"1.1.7","fileUrl":…}`），
跟本项目的版本号毫无关系。

更危险的是它旁边的诱惑：把请求头里的 `ver` 跟上去。`ver ≥ 3.5` 会触发服务端强制签名校验，
而本项目对那一段算法的实现是错的（实测十种变体全被拒），**后果是所有请求一起挂掉，
错误信息只有一句 `sign invalid`**。见 `bodian-api-reference.md` §1.3 与 `roadmap.md`
的长期维护表。

## 7. 砍掉的参照项

参照物（官方客户端）里有、本项目**不做**的：

| 项 | 理由 |
| --- | --- |
| 使用播放加速服务 | 官方专有；本项目音源授权完全交给 `checkRight`，不做客户端侧加速 |
| 联系客服 / 反馈历史 | 非官方第三方项目没有客服，也不含任何上报通道 |
| 下载相关设置 | 项目不做下载（音频不落盘，解密器刻意不编译进客户端） |
| 音频输出设备 | 要动全项目唯一碰 `MpvContext` 的地方（`LibMpvPlaybackService.EnsureInitialized`）加设备热插拔处理，成本与收益不匹配 |
| 关闭窗口行为开关 | 要把 `TrayCloseDecision` 从纯函数改成读设置，牵动单测与「唯一退出入口」的语义 |
| 全局热键 | 见 §3.1 |
