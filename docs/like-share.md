# 喜欢与分享

2026-10-03：播放栏与歌词页的「喜欢 / 分享」按钮从只读展示改为真实行为。此前 `8e07478` 只做了角标展示，
按钮明确标注「只读预留」，不绑定 `Command` 或 `Click`。

## 两个动作的性质完全不同

| 动作 | 性质 | 服务端 |
| --- | --- | --- |
| 喜欢 | **写操作**：把曲目加入 / 移出「我喜欢的」歌单 | `service/playlist/music` + `/delete`，**已完整往返实测** |
| 分享 | 链接本地拼 + **一次上报写操作** | `service/share/text`，每次调用该曲目分享数 +1 |

## 喜欢

### 端点

```
1. GET  service/playlist/fond?userId=<uid>          → data.id（「我喜欢的」歌单 id）
2. POST service/playlist/music                      signed  加歌
   POST service/playlist/music/delete               signed  删歌
   Body: {"playListId": <number>, "musicIdList": [<number>, ...]}
```

两条路径都在官方桌面端二进制里（`reverse/findings/06-library-api.md` §8），用默认 PC 请求头，**不带 android 头**。
`src=5` 只在取曲目时作为 query 的 `source`，写请求不带。

往返验证（`docs/bodian-api-reference.md` §2.4，2026-09-30 P0）：取歌单 `id=99980832` → 加歌读到 `total=1` →
删歌读到 `total=0`，四步都有读回确认。

### 喜欢的载体是歌单，不是「收藏」计数

服务端对一首歌的「是否已喜欢」**没有字段**。`service/music/info` 只给全站 `favorite` 计数
（`fixtures/music-info-228908.json` 的全部键里没有任何 `liked` / `isFond`）。所以：

- **判定**：客户端拿「我喜欢的」歌单 id，翻页取回它的曲目 id 集合，判断这首歌在不在里面。
- **计数**：角标显示的是全站 `favorite`，与当前账号的个人状态是两件事。
  ⚠️ **`favorite` 是否恰好等于「红心数」没有实测确认** —— 喜欢成功后角标 ±1 是按这个假设做的，
  第一次真实点击时要到「我喜欢的」页核对一次。

### 状态缓存与拉取时机

缓存只活在会话内，**不落盘**。落盘会让「在别的设备喜欢过」的状态长期不同步，
而重新拉一次的代价只有几个请求。

| 事件 | 行为 |
| --- | --- |
| 首次需要判定（进播放页 / 切歌） | 拉一次：`fond` 拿 id → 按 `rn=100` 翻页取完曲目 → 收成 `HashSet<long>` |
| 同一会话内之后的判定 | 直接用内存集合，**不发请求** |
| 喜欢 / 取消成功 | 本地集合立即改（入集 / 出集），并把缓存**标脏**；界面立刻正确 |
| 标脏后的下一次判定 | 重拉一次，拉完清标记；再往后又不再拉 |
| 登录 / 登出 / `11012` 清会话 | 会话 revision 变化 → 下一次判定重新拉 |

写操作后立刻重拉是冗余的（写入成功时结果已知），所以推迟到下一次判定，点击当下不发额外请求。

### 降级

`service/playlist/fond` 返回的对象缺 `id`，说明账号还没有「我喜欢的」歌单。
此时喜欢按钮无法工作：判定返回「未知」，点击提示原因。**本轮不新建歌单** ——
`POST service/playlist`（新建歌单）只有静态证据（`reverse/findings/11-share-playlist-crud.md`），
本项目从未发过一次真实请求，接入前必须先实测。

### 界面

| 位置 | 行为 |
| --- | --- |
| 播放栏曲目信息块右侧、歌词页左下角 | 空心心形 `EB51` = 未喜欢；实心 `EB52` = 已喜欢 |
| 未登录 | 点击提示「登录后可以喜欢」，不发请求 |
| 处理中 | 防止重复点击；切歌或返回后的迟到响应不覆盖新状态 |
| 失败 | 保持原状态并提示，不自动重试 |

## 分享

**链接不发请求，但那一次分享要上报 —— 上报只对歌曲成立**，歌手与专辑只复制链接，
见本节的「歌手与专辑」一小节。歌曲每次分享（含「复制链接」）都调一次
`service/share/text`，服务端据此把该曲目的分享数 +1 并返回分享文案
（2026-10-03 实测：`share` 从 2128 变 2129，`favorite` 不变）。

```
GET service/share/text
Query: shareTo=5&shareSource=0&sourceId=<musicId>&playlistType=4     signed
```

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `shareTo` | `5` | 分享目标枚举里的「复制链接」。**它同样计入分享数** |
| `shareSource` | `0` | 内容类型：歌曲 |
| `sourceId` | musicId | 内容 id |
| `playlistType` | `4` | 客户端默认值 |

响应 `data` 是 `{title, describe}` 文案。本项目不做系统分享面板，**用不到文案，因此不建模**。
业务码 `23006` 表示「该歌曲暂不支持分享」，按正常分支处理、不抛异常。

**顺序照官方：先上报 → 再拼链 → 再给用户。** 上报失败不影响复制 ——
链接是本地拼的，只有分享计数依赖服务端。

> **请求头与签名**：这是个安卓独有的端点，本项目用默认的 PC 请求头调它，与探针验证时一致。
> 探针的复现命令没带签名开关，而客户端一律带 `sign` —— 在钉死的 `ver=1.1.7` 下服务端不校验签名
> （见 `transport.md` 的版本门），所以两者等价；**升级 `ver` 之前要重新验证这条**。

链接由客户端本地拼（`allin/share/share_utils.dart::buildNowWebPageLink`）：

```
https://h5app.kuwo.cn/m/bodian/playMusic.html?uid={分享者uid}&musicId={歌曲id}&opusId={opusId}
```

- `uid` 是**分享者自己**的 uid，不是内容作者的；未登录时为 `-1`。
- **`opusId` 留空**：`Track` 模型里没有这个字段，且文档记它「分享歌曲时是否为空、为空时链接能否落地，未确认」。
  按官方模板原样保留 `&opusId=` 这个空参数位。
- host 可被远程配置覆盖，本项目不实现远程覆盖，写死常量。

**落地方式：复制到剪贴板**，并提示「已复制分享链接」。上报成功时角标 `share` +1；
`23006` 时提示「该歌曲暂不支持分享，链接已复制。」，计数不动。

### 歌手与专辑：只复制链接，不上报

**这两处不走 `service/share/text`** —— 点分享只把本地拼的链接写进剪贴板，不发任何请求。

| 内容 | 链接 | 上报 |
| --- | --- | --- |
| 歌手 | `singer.html?uid={uid}&singerId={id}` | ❌ 不做 |
| 专辑 | `album.html?uid={uid}&albumid={id}` | ❌ 不做 |

两条分属不同原因，别混为一谈：

- **歌手**：`shareSource=1` **已实测就是歌手**（同一个 `sourceId` 在 `0`/`1` 下分别返回歌名与歌手名），
  值不用再探。这里不做是<b>本轮的范围决定</b>：先只做复制链接。要加时照
  `ReportTrackShareAsync` 改一个 `shareSource` 即可。
- **专辑**：官方客户端的 `shareSource` 取什么值**没有证据**，所以是"不猜"而不是"不做"。

两条链接的参数名写法不一致（`singerId` 驼峰 / `albumid` 全小写），都逐字照抄
§2.8 的模板表，**不要顺手统一** —— 改错只会得到一条打不开的链接，没有任何一处会报错。
`ShareLinkTests` 里各有一条守着这件事。

### 已知风险

1. `opusId` 为空时链接能否正常落地，未验证 —— 需要人工打开一次确认。
2. 上报**不要求登录**（复制链接不该被登录态挡住），但匿名会话下服务端是否接受未实测。
3. 歌手与专辑的链接模板同样是静态证据（§2.8 记「分享链接模板 ❌ 未实测」），
   拼法对但页面能否打开未验证。

## 曲目行「更多」菜单（2026-10-03）

列表行尾的「更多」按钮（悬停才出现）把喜欢与「添加到歌单」下沉到了列表里，
另外两项是跳转：查看歌手、查看专辑。几何、悬停状态与已知取舍见
[`ui-refresh.md`](ui-refresh.md) §15。

| 项 | 走什么 |
| --- | --- |
| 我喜欢 | 与播放条同一套 `ILikedSongsService`，文案与失败处理一字不差 |
| 添加到歌单 | `POST service/playlist/music`（文档 2.4 已实测往返）。歌单列表来自 `GetCreatedPlaylistsAsync`，即**自建歌单**，「我喜欢的」不在这个列表里（文档 2.4） |
| 查看歌手 | 曲目自带的 `artists[0].id`；没有时现查一次 `service/music/info` 补（该端点不要求登录） |
| 查看专辑 | 曲目自带的 `albumId` —— 这一轮才把它从 DTO 映射进 `Track` |

**写入接口是通用的**：落点是红心歌单还是自建歌单，只差一个 `playlistId`。
但「新建歌单」仍然不做 —— `POST service/playlist` 至今只有静态证据（见上一节的降级说明）。

## 本轮不做

| 项 | 原因 |
| --- | --- |
| 系统分享面板（`DataTransferManager`） | 官方是 Flutter 插件拉起第三方面板；桌面端没有这条路径 |
| 分享文案 `{title, describe}` | 本项目没有分享面板，没有消费方 |
| 喜欢状态落盘 | 见「状态缓存」一节 |
| 账号没有「我喜欢的」歌单时自动新建 | 新建歌单端点未实测 |
| 行内直接摆心形按钮（不折叠进菜单） | 行内入口统一收进「更多」菜单，见上一节 |
